## 1. Decision summary

### Overall assessment

A small ASP.NET Core / EF Core service (MediatR-style handlers, SQLite by default, SQL Server optional) with no caching, metrics or load tests. The dominant risks are data-access shape rather than CPU: no secondary indexes on the columns every request filters on, and an unbounded, over-fetching article list. Nothing was measured; all findings are static, so none is `Confirmed`. Review confidence: Medium.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add indexes on Article.Slug, Person.Username, Person.Email, Article.CreatedAt | Every slug/user request scans without them; cheap to fix |
| 2 | **PERF-002 (P1)** | Clamp `limit`, project list rows (no Body, no favorite rows) | Unbounded work on the main browse endpoint |
| 3 | **PERF-003 (P2)** | Replace sync `Count()` with `CountAsync` | One-line change in the same handler as PERF-002 |

### Key unknowns

| Unknown | Decision it changes | How to resolve it |
|:--|:--|:--|
| Table sizes and concurrency | Severity of PERF-001/003/005 | Row counts and a load test on the target database |
| Deployed provider (SQLite vs SQL Server) | PERF-003 and PERF-007 impact | Deployment config |
| Actual SQL shape of list query | PERF-002 magnitude | EF command log from a test run |

### Validation commands

No repository-local command is justified (no benchmark or load-test project exists). Procedure: capture the query plan for `WHERE Slug = ?` and the `GET /articles` SQL with EF command logging on a representative dataset (`safe-on-production` on a replica).

## 7. Findings

### PERF-001 — No indexes on Slug, Username, Email, CreatedAt

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | High |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:62` |
| **Tags** | scalability-risk, needs-measurement |

**Problem:** The model defines no secondary indexes; slug, username and email lookups and the CreatedAt sort scan.
**Performance principle:** Selective lookups must be index-served (O(log n)).
**Evidence:** No `HasIndex`/`[Index]` anywhere; slug filters in Details, Comments, Favorites, Edit; username in all authenticated handlers; email in Login/Create; order by CreatedAt in List. Static only; no runtime evidence.
**Impact:** Critical path, per request, O(n), service-wide.
**Conditions:** Many thousands of rows (assumed).
**Counter-evidence:** Searched for indexes, migrations, raw DDL: none. Plans not available.
**Why this might not matter:** Demo-scale data makes scans cheap.
**Recommendation:** Add unique indexes on Slug, Username, Email and an index on (CreatedAt, ArticleId); adopt migrations.
**Alternatives:** HasIndex (preferred); cache by slug (masks scan).
**Trade-offs:** Write overhead; migration needs duplicate check.
**Validation:** Compare query plans before/after on representative data; falsified if plans already seek. `safe-on-production`.

### PERF-002 — Article list: unbounded, over-fetching

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity / Confidence / Priority** | High / High / P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/List.cs:31` |
| **Tags** | scalability-risk |

**Problem:** `limit` has no cap; Author, all favorites and tags are joined per article; Body is loaded then nulled.
**Performance principle:** Bound per-request work; fetch only what the response uses.
**Evidence:** `List.cs:109`, `ArticleExtensions.cs:11`, `List.cs:114`, `Article.cs:21`. No runtime evidence.
**Impact:** Critical path, per request, O(n), amplification Nx (favorites x tags rows).
**Conditions:** Clients requesting large limits; articles with many favorites/tags (assumed).
**Counter-evidence:** No clamp or validator found; default 20 bounds the common case.
**Why this might not matter:** Default page is 20 and favorites/tags per article may be small.
**Recommendation:** Clamp limit/offset; project to DTO with counts instead of favorite rows; omit Body in the query.
**Alternatives:** Cap + projection (preferred); split queries (more round trips).
**Trade-offs:** Output shape must stay identical; clamp is a visible behavior change.
**Validation:** Rows/bytes per request at default and large limit; `safe-on-production`; falsified if SQL shows no duplication.

### PERF-003 — Synchronous Count() in async handler

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity / Confidence / Priority** | Medium / High / P2 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Features/Articles/List.cs:133` |
| **Tags** | quick-win |

**Problem:** `queryable.Count()` blocks a thread-pool thread inside async code.
**Performance principle:** Do not block threads on I/O in async paths.
**Evidence:** `List.cs:133`; no runtime evidence.
**Impact:** Critical path, per request, O(n) count, service blast radius.
**Conditions:** High concurrency on SQL Server or a large unindexed table (assumed).
**Counter-evidence:** SQLite is in-process, so impact is lower there.
**Why this might not matter:** Under SQLite the difference is small.
**Recommendation:** `await CountAsync(cancellationToken)`.
**Alternatives:** CountAsync (preferred); drop/approximate count (API change).
**Trade-offs:** None significant.
**Validation:** Thread-pool queue length under concurrent load; `not-safe-on-production`.

### PERF-004 — Whole comment collection loaded for single-row operations

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity / Confidence / Priority** | Medium / High / P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Comments/Create.cs:37` |
| **Tags** | scalability-risk |

**Problem:** Create/Delete include all comments to add/remove one; List returns all with authors, unpaged.
**Performance principle:** Do not materialize an unbounded collection for a one-row operation.
**Evidence:** `Create.cs:37`, `List.cs:23`, `Delete.cs:29`. Static only.
**Impact:** Critical path, per request, O(n) in comments per article, endpoint.
**Conditions:** Articles with many comments (assumed).
**Counter-evidence:** Spec returns all comments, bounding paging options.
**Why this might not matter:** Typical comment counts are small.
**Recommendation:** Query only the needed article id/comment; project and optionally cap List.
**Alternatives:** Targeted queries (preferred); cache lists (invalidation cost).
**Trade-offs:** Paging beyond the spec is a contract change.
**Validation:** Rows loaded by POST comment on a heavily commented article; `safe-on-production`.

### PERF-005 — Follow sets loaded in full for membership tests

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity / Confidence / Priority** | Medium / High / P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Profiles/ProfileReader.cs:37` |
| **Tags** | scalability-risk |

**Problem:** ReadProfile includes Following and Followers to check one relation; feed and list load all followed ids into memory.
**Performance principle:** Use keyed existence queries for membership.
**Evidence:** `ProfileReader.cs:37`, `List.cs:38`, `List.cs:123`. Static only.
**Impact:** Critical path, per request, O(n) in follow count, endpoint.
**Conditions:** Users with large follower/following sets (assumed).
**Counter-evidence:** No limits on follows found.
**Why this might not matter:** Most users have few follows.
**Recommendation:** `AnyAsync` on (ObserverId, TargetId); restrict list decoration to page authors.
**Alternatives:** Keyed queries (preferred); cache (staleness).
**Trade-offs:** A few extra small queries.
**Validation:** Rows loaded for GET /profiles/{username}; `safe-on-production`.

### SEC-001 — Weak password hashing and hard-coded keys

| | |
|:--|:--|
| **Kind** | Security |
| **Confidence** | High |
| **Risk** | High (credentials hashed with one fast keyed pass using a literal key; JWT signing key is in source) |
| **Location** | `src/Conduit/Infrastructure/Security/PasswordHasher.cs:12` |

**Problem:** Single HMAC-SHA512 with a literal key; JWT key/issuer/audience hard-coded; non-constant-time hash comparison.
**Evidence:** `PasswordHasher.cs:12`, `ServicesExtensions.cs:50`, `Login.cs` SequenceEqual.
**Impact:** Leaked hashes are cheap to crack; anyone with the source can forge tokens.
**Recommendation:** Use a slow KDF and externalized secrets.
**Trade-offs:** Slower login by design; secret management needed.
**Validation:** Dedicated security review.
**Would need:** A security review and secret/dependency scan.
