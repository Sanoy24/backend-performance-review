## 1. Decision summary

### Overall assessment

A small ASP.NET Core (MediatR-style `Mediator`, EF Core, SQLite default, SqlServer selectable) RealWorld API with no instrumentation or load evidence. The code is clean and mostly async, but two things are structural: every request passes through a pipeline behavior that opens and commits the transaction synchronously, and the hot lookup keys (slug, username, email) have no declared indexes. The article list endpoint is also unbounded and over-fetches. Review confidence is Medium: source-only, workload and data volumes unknown.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-003 (P1)** | Add unique indexes on `Article.Slug`, `Person.Username`, `Person.Email` | Hit on nearly every request; cost grows with table size; cheap to fix |
| 2 | **PERF-001 (P1)** | Switch the transaction behavior to `BeginTransactionAsync`/`CommitAsync`/`RollbackAsync` | Blocking call on every request, shared thread pool |
| 3 | **PERF-004 (P2)** | Cap `limit`, stop fetching `Body` and full favorite rows in list | Client-controlled unbounded work on the main read endpoint |

## 7. Findings

### PERF-001 — Synchronous transaction begin/commit on every request

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | High |
| **Priority** | P1 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs:27` |

**Problem**
The behavior wrapping every request calls synchronous `BeginTransaction()`/`CommitTransaction()` (`Database.BeginTransaction`, `Commit`) in an async handler.

**Performance principle**
Do not hold a shared worker thread across I/O.

**Evidence**
`DBContextTransactionPipelineBehavior.cs:27,31`; `ConduitContext.cs:103,111`; registered for all requests at `ServicesExtensions.cs:26`. No runtime evidence exists.

**Impact**
Critical path, per request, grows with concurrency, system-wide (shared thread pool).

**Conditions**
SqlServer provider and concurrency above the thread-pool minimum. On default SQLite the call is cheap.

**Counter-evidence**
No async transaction use or read-only skip found. Default provider SQLite lowers impact (bounds-impact).

**Why this might not matter**
At low concurrency or on in-process SQLite the blocked window is tiny.

**Recommendation**
Use `BeginTransactionAsync`, `CommitAsync`, `RollbackAsync`; consider skipping the transaction for read queries.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Async transaction APIs | **preferred** | Removes blocking at the source |
| `ThreadPool.SetMinThreads` | | Masks the problem |
| Skip tx for reads | | Complementary |

**Trade-offs**
Interface becomes async; reads without a transaction lose snapshot consistency.

**Validation**
`dotnet-counters` thread-pool queue length under load, before and after (safe-on-production for the counters; the load test itself is not-safe-on-production). Falsifier: no queue growth at target concurrency.

### PERF-002 — Synchronous `Count()` in article list

Medium / High / P2, concurrency, `src/Conduit/Features/Articles/List.cs:133`, ROOT-001. `queryable.Count()` is synchronous and re-runs the query with all Includes. Evidence: `List.cs:133`, async calls elsewhere in the same handler (`:111`). Impact: critical path, per request, O(n), system-wide. Conditions: concurrency above the pool minimum; table size unknown. Counter-evidence: no cheaper count exists; small tables bound the window. Why it might not matter: short single query. Recommendation: `CountAsync` on a query without the Includes. Alternatives: omit count (breaks contract). Trade-offs: predicates must stay shared. Validation: query log shows count without joins; falsifier: negligible time (safe-on-production).

### PERF-003 — No indexes on Slug, Username, Email

High / High / P1, data-access, `src/Conduit/Domain/Article.cs:14`, ROOT-002, tag scalability-risk.

**Problem**: Hot lookup keys have no declared index or unique constraint; EF Core indexes only FKs by convention.
**Evidence**: no `HasIndex`/`[Index]` anywhere (`ConduitContext.cs:21`); slug lookups across Details/Edit/Delete/Comments/Favorites; Username lookup in `Favorites/Add.cs:41`, Create, ProfileReader; Email in `Login.cs:49`; schema via `EnsureCreated` and no migrations (`Program.cs:124`). No runtime evidence.
**Impact**: critical path, per request, O(n) in table size, system-wide.
**Conditions**: tables beyond cheap-scan size; counts unknown.
**Counter-evidence**: an out-of-band index cannot be ruled out (lowers confidence slightly; kept High because the model is the only schema source in the repository). Slug uniqueness also unenforced (probe loops are racy).
**Why this might not matter**: demo-sized tables of a few thousand rows scan cheaply.
**Recommendation**: unique indexes on the three keys, with a migration path.
**Alternatives**: cache current user (invalidation cost; index is cheaper, preferred).
**Trade-offs**: insert overhead; unique constraint can fail on existing duplicates; `EnsureCreated` will not alter an existing DB.
**Validation**: `sqlite3 realworld.db "EXPLAIN QUERY PLAN SELECT * FROM Articles WHERE Slug = 'x';"` (safe-on-production). Falsifier: plan already uses an index.

### PERF-004 — Article list unbounded and over-fetching

Medium / High / P2, data-access, `src/Conduit/Features/Articles/List.cs:105`, ROOT-003.

**Problem**: `limit` has no cap; OFFSET pagination; two sibling collection Includes in one query; `Body` loaded then nulled.
**Evidence**: `List.cs:109,116`; `ArticleExtensions.cs:11-13`; `Domain/Article.cs:24`. No runtime evidence.
**Impact**: critical path, per request, O(n), service-wide; row product favorites x tags is derived from the join shape, magnitude unknown.
**Conditions**: large limit, articles with many favorites/tags, deep offsets.
**Counter-evidence**: default page 20 bounds the common case; no global page cap found.
**Why this might not matter**: default limit and typical counts keep the product small.
**Recommendation**: clamp limit; project to a DTO without Body using a favorite count; split query or subqueries; keyset pagination if deep offsets matter.
**Alternatives**: `AsSplitQuery` only (still loads Body and full favorites).
**Trade-offs**: serialization shape changes; clamp changes client behavior.
**Validation**: query log rows/bytes per page for an article with many favorites and tags (safe-on-production). Falsifier: no multiplication at realistic counts.

### PERF-005 — Unbounded comments and tags reads

Medium / High / P2, data-access, `src/Conduit/Features/Comments/List.cs:22`, ROOT-004. Comments load the article plus all comments and authors, tracked (`Comments/List.cs:22`); tags loads the whole table each request (`Tags/List.cs:22`). Impact: per request, O(n), endpoint. Conditions: large threads or tag tables (unknown). Counter-evidence: the spec returns both unpaged. Why it might not matter: small tables. Recommendation: `AsNoTracking` and projection for comments; cap or briefly cache tags. Alternatives: paging (breaks spec). Trade-offs: short staleness. Validation: response size and query time (safe-on-production); falsifier: counts in the tens.

---

### PERF-006 — Whole follow collections loaded for membership tests

Medium / Medium / P2, data-access, `src/Conduit/Features/Profiles/ProfileReader.cs:36`, ROOT-005. `Include(Following).Include(Followers)` to test one id (Following unused); list/feed load follow sets (`List.cs:37,123`). Impact: per request, O(n) in follow count, endpoint. Conditions: users with many follows (unknown, hence Medium). Counter-evidence: modest counts expected. Why it might not matter: tens of follows are cheap. Recommendation: `AnyAsync` and page-scoped follow query. Trade-offs: minor. Validation: rows materialized per request (safe-on-production); falsifier: follow counts of a few dozen.

### SEC-001 — Hard-coded signing and hashing keys, fast password hash

| | |
|:--|:--|
| **Kind** | Security |
| **Confidence** | High |
| **Risk** | High (anyone with source can forge tokens; passwords use one fast HMAC pass) |
| **Location** | `src/Conduit/ServicesExtensions.cs:48`, `Infrastructure/Security/PasswordHasher.cs:11` |

**Problem** JWT signing key and HMAC key are literals in source; password hashing is a single HMAC-SHA512 pass.
**Evidence** `ServicesExtensions.cs:48`; `PasswordHasher.cs:11-22`.
**Impact** Token forgery and cheap offline cracking if the source or database leaks.
**Recommendation** Load keys from secret configuration; use PBKDF2/Argon2.
**Trade-offs** Slower login by design; key rotation process needed.
**Validation** Run the dedicated review.
**Would need** A dedicated security review.
