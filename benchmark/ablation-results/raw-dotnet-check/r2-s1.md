## 1. Decision summary

### Overall assessment

A small ASP.NET Core (net10) + EF Core + SQLite service with no cache, broker or outbound calls. The material risks are data-access shape, not concurrency: natural-key lookups (slug, username, email) have no indexes, and the article list accepts an unbounded page size over an over-fetching eager-load. All findings are static readings with no runtime evidence; review confidence is Medium.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add unique indexes on Slug, Username, Email in `OnModelCreating` | Every request path filters on these; scan cost grows with table size |
| 2 | **PERF-002 (P1)** | Clamp `limit`/`offset` in the article list | Unauthenticated, one request can load the whole table |
| 3 | **PERF-003 (P2)** | Replace the three sibling `Include`s with a projection | Row count multiplies favorites x tags; shared by four endpoints |

### Key unknowns

| Unknown | Decision it changes | How to resolve it |
|:--|:--|:--|
| Table sizes (articles, favorites, users) | Severity of PERF-001/002/003 | Row counts on a production-sized copy |
| Request concurrency and real DB provider | Priority of PERF-004/005 | `dotnet-counters` under load |
| Whether a proxy caps `limit` or response size | PERF-002 exposure | Deployment config |

### Validation commands

- `safe-on-production` `sqlite3 realworld.db "EXPLAIN QUERY PLAN SELECT * FROM Articles WHERE Slug = 'x';"` (run on a copy) shows scan vs seek (PERF-001).
- `not-safe-on-production` `curl -s "http://localhost:8080/api/articles?limit=100000" | wc -c` against a local seeded instance (PERF-002).
- `safe-on-production` `dotnet-counters monitor --process-id <pid> System.Runtime` for thread-pool queue length (PERF-004/005).

## 7. Findings

### PERF-001 — No indexes on slug, username, email lookups

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | High |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:36` |
| **Tags** | scalability-risk |

**Problem** The model declares only composite keys and FKs. Slug, Username and Email are filtered on constantly but unindexed, so lookups scan.

**Performance principle** Lookups by a filtered value need an access path independent of table size.

**Evidence** `OnModelCreating` has no `HasIndex`; no index anywhere in `src`. Schema is `EnsureCreated` only (`Program.cs`). Slug lookups: `Features/Articles/Details.cs:32`; Email: `Features/Users/Login.cs:50`; slug-suffix loop: `Features/Articles/Create.cs:72`. No runtime evidence.

**Impact** Critical path, per request, O(n) in rows, system-wide.

**Conditions** Large Articles/Persons tables (assumed many thousands; sizes unknown).

**Counter-evidence** Searched for indexes, attributes, migrations: none. FK id columns are indexed by the provider, bounding only id joins. Table size unknown.

**Why this might not matter** Demo-scale data never pays the scan; indexes cost writes and disk.

**Recommendation** Add unique indexes on Slug, Username, Email, plus one supporting `CreatedAt DESC`. They also enforce uniqueness the code only checks.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Model-level unique indexes | **preferred** | Removes scan at its cause |
| Cache slug lookups | | Masks the scan |

**Trade-offs** Slower writes, extra storage; adding unique indexes can fail on existing duplicates.

**Validation** `safe-on-production`: `sqlite3 realworld.db "EXPLAIN QUERY PLAN SELECT * FROM Articles WHERE Slug = 'x';"` on a copy. Expect SCAN to become SEARCH. Falsifier: plan already seeks.

### PERF-002 — Unbounded page size on article list

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | High |
| **Confidence** | High |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/List.cs:108` |
| **Tags** | scalability-risk |

**Problem** `limit` and `offset` flow from the query string to `Take`/`Skip` unchecked, so one request can pull the whole table; offset paging also reads skipped rows.

**Performance principle** Client-derived response size must be capped.

**Evidence** `List.cs:108-109`; `ArticlesController.cs:20` binds plain `int?`; no validator for `List.Query`. Sort on unindexed `CreatedAt` (`List.cs:106`). No runtime evidence.

**Impact** Critical path, per request, O(n), service-wide (memory and DB time).

**Conditions** Any client sending a large limit or paging deep; scales with article count (unknown).

**Counter-evidence** No max-page-size found; default 20 only helps cooperative clients.

**Why this might not matter** Only abusive clients trigger it; a proxy may cap responses.

**Recommendation** Clamp limit, reject negative offset; keyset paging if deep paging matters.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Clamp in handler/validator | **preferred** | Smallest bounding change |
| Keyset pagination | | Changes API contract |
| Proxy rate limit | | Does not bound one request |

**Trade-offs** Clients get fewer items than asked.

**Validation** `not-safe-on-production`: `curl -s "http://localhost:8080/api/articles?limit=100000" | wc -c` on a local seeded instance. Expect capped rows afterwards.

### PERF-003 — Eager-load helper multiplies rows and over-fetches

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/ArticleExtensions.cs:9` |
| **Tags** | scalability-risk |

**Problem** `GetAllData` includes Author, ArticleFavorites and ArticleTags in one query (no `AsSplitQuery`), yielding favorites x tags rows per article, and loads all favorite rows just to count them.

**Performance principle** Do not fetch or join more than the response needs.

**Evidence** `ArticleExtensions.cs:9`; counts computed in memory (`Domain/Article.cs:25`); used by list, details, edit and favorite add. Derivation: up to 20 x F x T rows per page of 20. No runtime evidence.

**Impact** Critical path, per item, superlinear in favorites x tags, endpoint-wide.

**Conditions** Articles with many favorites and several tags; distribution unknown.

**Counter-evidence** No split-query configuration. The list `Count()` drops includes, so it is unaffected.

**Why this might not matter** Small tag/favorite counts keep the product tiny.

**Recommendation** Project to a DTO with a count subquery and a tag list, or `AsSplitQuery`.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Projection with Count subquery | **preferred** | Removes blow-up and row transfer |
| AsSplitQuery | | Still transfers every favorite |

**Trade-offs** Larger mapping rewrite; split queries add round trips.

**Validation** `not-safe-on-production`: enable EF command logging locally and count rows returned for a seeded article. Expect one row per article.

### PERF-004 — Synchronous transaction calls on every request

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs:27` |
| **Tags** | needs-measurement |

**Problem** The shared behavior calls sync `BeginTransaction`/`Commit` (`ConduitContext.cs:103`) twice per request, including read-only GETs.

**Performance principle** Do not block a shared worker thread; skip unneeded work.

**Evidence** `DBContextTransactionPipelineBehavior.cs:27,31`; registration `ServicesExtensions.cs:27`. No runtime evidence.

**Impact** Critical path, per request, O(1), system-wide (thread pool).

**Conditions** High concurrency with a provider that waits on I/O; load unknown.

**Counter-evidence** Provider is hard-coded to SQLite (`Program.cs:17`), whose async calls complete synchronously, so today's penalty is small. Confidence is lowered accordingly.

**Why this might not matter** Embedded SQLite has no network wait to hide.

**Recommendation** Use async transaction APIs; wrap commands only, not queries.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Async calls + query/command split | **preferred** | Fixes both issues |
| Remove behavior | | Breaks multi-save atomicity |

**Trade-offs** Multi-`SaveChanges` handlers rely on the outer transaction.

**Validation** `safe-on-production`: `dotnet-counters monitor --process-id <pid> System.Runtime` under load; falsifier is no queue growth at target concurrency.

### PERF-005 — Synchronous Count on the list endpoint

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Features/Articles/List.cs:133` |
| **Tags** | quick-win |

**Problem** `queryable.Count()` blocks the request thread on the busiest endpoint, as an extra count per call.

**Performance principle** Do not block a shared worker thread on I/O.

**Evidence** `List.cs:133`; all other calls in the handler are async. No runtime evidence.

**Impact** Critical path, per request, O(n), system-wide.

**Conditions** Concurrent list traffic against a networked DB; SQLite offsets this.

**Counter-evidence** SQLite default (`Program.cs:17`) lowers practical effect.

**Why this might not matter** One-line change, small effect on SQLite; count is required by the contract.

**Recommendation** `await CountAsync(cancellationToken)`.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| CountAsync | **preferred** | Same semantics |
| Drop count | | Breaks `articlesCount` |

**Trade-offs** None meaningful.

**Validation** `safe-on-production`: thread-pool queue length during concurrent list calls.

### SEC-001 — Weak password hashing and hard-coded keys

| | |
|:--|:--|
| **Kind** | Security |
| **Confidence** | High |
| **Risk** | High |
| **Location** | `src/Conduit/Infrastructure/Security/PasswordHasher.cs:11` |

**Problem** One HMAC-SHA512 pass with a hard-coded key and no work factor; JWT key and issuer are literals in source; hashes compared with `SequenceEqual`.

**Evidence** `PasswordHasher.cs:11`; `ServicesExtensions.cs:62`; `Features/Users/Login.cs:64`.

**Impact** Leaked hashes are cheap to brute-force and a source-visible JWT key allows token forgery: High risk.

**Recommendation** Use a slow KDF (PBKDF2/Argon2/Identity hasher), load the JWT key from secrets, constant-time compare.

**Trade-offs** A proper KDF adds deliberate CPU per login.

**Validation** Run the dedicated review below.

**Would need** A dedicated security review of authentication and secrets handling.
