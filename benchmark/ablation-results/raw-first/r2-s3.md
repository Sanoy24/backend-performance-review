## 1. Decision summary

### Overall assessment

A small, conventional FastAPI + SQLModel + PostgreSQL CRUD service with sync handlers. Nothing is structurally broken. The one issue worth acting on is a missing index on `item.owner_id`, which makes every owner-scoped item list and user-delete scan the item table as it grows. Two smaller issues concern connection hold time and unbounded page size. No runtime evidence exists, so review confidence is Medium and all findings are static.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add an Alembic migration with an index on `item (owner_id, created_at)` | Per-request scan growing with data; cheap fix |
| 2 | **PERF-002 (P2)** | Move SMTP sends to background tasks, set a timeout, release the DB session before hashing/sending | Pool connections held across slow work on unauthenticated routes |
| 3 | **PERF-003 (P3)** | Cap `limit` with `Query(le=...)` | One-line bound on response size |

## 7. Findings

### PERF-001 — Unindexed item.owner_id on owner-scoped list, count and delete

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `backend/app/api/routes/items.py:14` (`read_items`) |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Item queries filter on `owner_id` and sort by `created_at`, but neither is indexed, so each non-superuser list (count plus page) and the bulk item delete in user deletion scan the item table.

**Performance principle**
Selective lookups should cost proportional to the result, not the dataset size.

**Evidence**
`models.py:97` declares `owner_id` as a foreign key without `index=True`; the migrations create only `ix_user_email` (`e2412789c190_initialize_models.py:33`); `items.py:30-45` filters on `owner_id`; `users.py:244` deletes by `owner_id`. No runtime evidence exists.

**Impact**
Critical path, per request, O(n) in table size, service-wide (shared Postgres). Two queries per list call.

**Conditions**
Matters when the item table is large enough that a scan outweighs an index lookup. Size unknown; negligible on small tables.

**Counter-evidence**
Searched models and migrations for any item index; found none. PostgreSQL does not auto-index foreign key referencing columns (database behaviour, not repo-stated). No EXPLAIN or row counts, so confidence capped at Medium.

**Why this might not matter**
If the table stays at a few thousand rows (this is a starter template), the scan is cheap and the index only adds write cost.

**Recommendation**
Add a composite index on `item (owner_id, created_at)` via Alembic; it serves the filter, count, ordered page and cascade delete.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Composite index (owner_id, created_at) | **preferred** | Covers filter and sort |
| Single index on owner_id | | Leaves a sort per request |
| Do nothing until measured | | Fine if growth is bounded |

**Trade-offs**
Extra write cost and storage; build concurrently to avoid blocking writes.

**Validation**
See §9.

### PERF-002 — Connections held across SMTP and Argon2 work

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/api/routes/login.py:54` (`recover_password`) |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Sync handlers keep a request-scoped DB session open, so a pooled connection is held once a query has run, while doing slow non-DB work: SMTP in password recovery and user creation, and Argon2 verification in login.

**Performance principle**
Do not hold a scarce shared resource across slow work that does not need it.

**Evidence**
`deps.py:21` session closes at end of request; `login.py:54-70` queries then sends email on an unauthenticated route; `utils.py:47` sets no SMTP timeout; `crud.py:45` verifies the hash (parameters m=65536, t=3, p=4 per `DUMMY_HASH`) while the session is open; `db.py:7` uses default pool settings; Dockerfile uses 4 workers. No runtime evidence.

**Impact**
Critical path, per request, O(1) per request but concurrency-bound, service-wide through pool exhaustion.

**Conditions**
SMTP enabled and slow/unreachable, or many concurrent login/recovery attempts (including abusive traffic) approaching the per-worker pool limit. Both unknown.

**Counter-evidence**
Threadpool handlers do not block the event loop (bounds impact). Whether the connection stays checked out after the first query depends on SQLAlchemy transaction semantics, not verified at runtime (lowers confidence).

**Why this might not matter**
Email is infrequent and usually fast; at low traffic the pool never saturates.

**Recommendation**
Send email via BackgroundTasks or a queue with a socket timeout; end the transaction or close the session before hashing and sending; rate-limit recovery and login.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| BackgroundTasks + early session release | **preferred** | Removes the coupling cheaply |
| Larger pool | | Masks it; bounded by Postgres max connections |
| Task queue | | More ops burden than evidence justifies |

**Trade-offs**
Loses error propagation from background email; session handling needs care.

**Validation**
See §9.
