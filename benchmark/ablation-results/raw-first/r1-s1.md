## 1. Decision summary

### Overall assessment

A small, conventional synchronous FastAPI + SQLModel + PostgreSQL CRUD service with no committed measurements, so every finding is static and capped at Medium confidence. The most important point is a missing index on `item.owner_id`, which every owner-scoped item list and every user deletion depends on. A second, workload-dependent risk is that login, password-change and password-recovery handlers hold a pooled DB connection while doing Argon2 hashing or SMTP. Review confidence: Medium.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add a composite `(owner_id, created_at DESC)` index on `item` via Alembic | Grows with the item table on the main read path; cheap, low risk |
| 2 | **PERF-002 (P2)** | Release the DB transaction before Argon2 and move SMTP out of the request; set pool limits explicitly | Unauthenticated endpoints can pin threads and connections |
| 3 | **PERF-003 (P3)** | Cap `limit` with `Query(le=...)` | Quick win |

## 3. Architecture overview

A single backend service (`fastapi run --workers 4`) behind Traefik, using PostgreSQL 18 through SQLModel/SQLAlchemy with the psycopg driver, Alembic migrations, JWT auth, Argon2/bcrypt via pwdlib, optional SMTP and Sentry. Handlers are plain `def` (run in a threadpool) except `health_check`. One `Session` per request (`get_db`).

| Component | Technology | Version | Support tier | Role |
|:--|:--|:--|:--|:--|
| API | FastAPI | >=0.141.1 | Generic | HTTP surface |
| ORM | SQLModel / SQLAlchemy | >=0.0.39 | Generic | Data access |
| Database | PostgreSQL | 18 | Conceptual | Users and items |
| Hashing | pwdlib Argon2 + bcrypt | >=0.3.0 | Generic | Password verification |
| Email | `emails` (smtplib) | >=1.1.2 | Generic | Recovery and account mail |

**Shared resources:** per-worker SQLAlchemy pool (no size set), sync handler threadpool, one PostgreSQL primary. No cache or broker.

## 7. Findings

### PERF-001 — Missing index on item.owner_id

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `backend/app/models.py:97` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
`item.owner_id` has a foreign key but no index in the model or any migration, yet `GET /items/` filters, counts and sorts by it, and user deletion cascades through it.

**Performance principle**
A lookup by a non-key attribute over a growing set must be served by an access path whose cost does not grow with the whole table.

**Evidence**
- `models.py:97` declares `owner_id` with foreign key and `ondelete="CASCADE"`, no `index=True` (contrast `User.email`).
- `items.py:14` (`read_items`) issues count and page queries with `WHERE owner_id = ...` ordered by `created_at DESC`.
- The only `create_index` in all migrations is `ix_user_email` (`e2412789c190...py:33`).
- `users.py:228` deletes items by `owner_id`; the FK cascade needs the same lookup.
- No runtime evidence exists in the repo.

**Impact**
Critical path, per request, growth O(n) in total item rows, blast radius service (shared DB). Two statements per request (derived).

**Conditions**
Matters once the item table is large enough that a sequential scan beats nothing (assumed tens of thousands of rows or more; actual count unknown).

**Counter-evidence**
PostgreSQL does not auto-index referencing FK columns, and no other index is defined (searched `Index(`, `create_index`, `index=True`). On tiny tables a scan is cheap, which lowered confidence to Medium.

**Why this might not matter**
This is a template; many deployments have small tables where a scan is as fast as an index.

**Recommendation**
Add a composite index `(owner_id, created_at DESC)` in an Alembic migration; it serves the filter, count, sort and cascade paths.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Single-column `owner_id` index | | Leaves the sort |
| Composite `(owner_id, created_at DESC)` | **preferred** | One structure for filter and order |
| Cache item pages | | Masks the scan; adds invalidation |

**Trade-offs**
Slightly slower writes and more storage; use `CREATE INDEX CONCURRENTLY` on large live tables.

**Validation**
Baseline `EXPLAIN (ANALYZE, BUFFERS)` plan on a staging copy (`not-safe-on-production`); expect Seq Scan to become Index Scan. Falsifier: plan already uses an index or table is small. `SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'item';` (`safe-on-production`).

### PERF-002 — DB connection and thread held across Argon2 and SMTP

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/crud.py:45` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Login, password-change and password-recovery handlers perform memory-hard Argon2 hashing or a blocking SMTP send while the request session's connection and transaction remain open.

**Performance principle**
Scarce shared resources should not be held across slow work that does not need them.

**Evidence**
- `crud.py:45` `authenticate` reads the user then runs `verify_password` before the session closes; unknown users still pay a full hash via `DUMMY_HASH` (m=65536, t=3, p=4).
- `login.py:54` `recover_password` queries the user then calls blocking `send_email` (no timeout option set, `utils.py:55`); endpoint is unauthenticated.
- `users.py:104` `update_password_me` verifies and re-hashes while holding the session.
- `db.py:7` `create_engine` sets no pool options; `Dockerfile` runs 4 workers, each with its own pool.
- Derived: 65536 KiB = 64 MiB transient memory per concurrent hash; no container memory limit in `compose.yml`.
- No runtime evidence.

**Impact**
Critical path, per request on those endpoints, growth unknown, blast radius service (pool and threads are shared with all endpoints in the worker).

**Conditions**
Concurrent login/recovery requests approaching a worker's threadpool or pool limit (credential stuffing, bursts, slow SMTP). Concurrency and SMTP latency are unknown.

**Counter-evidence**
Handlers are `def`, so the event loop is not blocked; Argon2 libraries typically release the GIL. No rate limiting, pool configuration or background email found. Hash cost is deliberate.

**Why this might not matter**
Logins are a small share of traffic, and with modest load or a fast SMTP relay the limits are never reached.

**Recommendation**
End the transaction before hashing (and copy needed fields), send mail via background task with an explicit SMTP timeout, set pool size/overflow/timeout explicitly, and rate-limit login and recovery.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Release connection early, background email | **preferred** | Removes the held resource, keeps hash strength |
| Increase pool size | | Multiplies across 4 workers; not shorter holds |
| Lower Argon2 cost | | Weakens security |

**Trade-offs**
Background email loses synchronous errors; early transaction end needs care with ORM expiry; rate limiting needs shared state.

**Validation**
Measure pool checkout wait and `idle in transaction` counts under concurrent login load (staging). `SELECT state, count(*) FROM pg_stat_activity WHERE datname='app' GROUP BY state;` (`safe-on-production`). Falsifier: no pool wait or queueing at expected concurrency.
