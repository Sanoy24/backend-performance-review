## 1. Decision summary

### Overall assessment

A small, conventional FastAPI + SQLModel + PostgreSQL CRUD service with sync handlers. No pathological hot-path code was found (no N+1, no event-loop blocking, no per-request full-table work other than a probable missing index). The most important item is the unindexed `item.owner_id` used by the main list endpoint (PERF-001). All findings are static; nothing in the repo is instrumented, so review confidence is Medium and no finding is `Confirmed`.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Run `EXPLAIN` on the items list query against a production-sized copy; if it seq-scans, add an `(owner_id, created_at DESC)` index via Alembic | Cheap to verify, grows linearly with table size |
| 2 | **PERF-003 (P2)** | Add `ge`/`le` bounds on `limit` and `skip` for `/items/` and `/users/` | One-line quick win; removes caller-controlled unbounded work |
| 3 | **PERF-002 (P2)** | Move `send_email` to a background task with an SMTP timeout | Stops SMTP latency pinning DB connections on an unauthenticated endpoint |

### Key unknowns

| Unknown | Decision it changes | How to resolve it |
|:--|:--|:--|
| Item row count and `/items` call rate | Severity of PERF-001 and PERF-003 | Row counts and request metrics from production |
| SMTP relay latency and whether email is enabled | Whether PERF-002 matters | Check env config; time a send |
| Argon2 cost in the deployed container, and any proxy rate limit | Whether PERF-004 is worth acting on | Time one hash; inspect proxy config |

### Validation commands

## 7. Findings

### PERF-001 — Unindexed `item.owner_id` on the list/count path

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `backend/app/models.py:97` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
`item.owner_id` is a foreign key with no index, yet the main authenticated list endpoint filters, counts and sorts items by it on every call.

**Performance principle**
Access paths must keep the cost of a selective lookup proportional to the rows returned, not to the table size.

**Evidence**
- `Item.owner_id` has `foreign_key`/`ondelete` but no `index=True` (`models.py:97`), whereas `User.email` does set it.
- Migrations create only `ix_user_email` (`e2412789c190_initialize_models.py:33`); the UUID migration re-creates `owner_id` with only an FK constraint.
- `read_items` runs `count(*) WHERE owner_id` and a filtered, ordered `OFFSET/LIMIT` page on each call (`items.py:23`); `delete_user` also deletes by `owner_id`.
- No runtime evidence (no `EXPLAIN`, no row counts) exists.

**Impact**
Position: critical path. Frequency: per request. Growth: O(n) in table size. Blast radius: endpoint (shared DB CPU/IO if large).

**Conditions**
Many thousands of items and frequent list calls; for a small table the planner may legitimately prefer a seq scan. Table size and call rate are unknown.

**Counter-evidence**
Searched migrations and models for any index on `item.owner_id` or a composite; none. Table size is unstated, so confidence is capped at Medium.

**Why this might not matter**
In a starter app with few items per user, the scan costs microseconds and an extra index only adds write overhead.

**Recommendation**
Add an Alembic migration with a composite index `(owner_id, created_at DESC)` and `index=True` on the field; use `CREATE INDEX CONCURRENTLY` on populated tables.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Composite index (owner_id, created_at DESC) | **preferred** | Serves filter, count and ordering |
| Single-column index on owner_id | | Fixes filter, still sorts |
| Do nothing until measured | | Fine if table stays small |

**Trade-offs**
Extra write cost and storage; concurrent index creation needed on large tables.

**Validation**
Baseline with `pg_stat_user_tables` and `EXPLAIN (ANALYZE, BUFFERS)` (see §9). Expect Seq Scan to become an index scan. Falsifier: plan already uses an index or table is small.

### PERF-002 — SMTP sent synchronously while holding a DB session

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/utils.py:33` |
| **Tags** | scalability-risk |

**Problem**
`send_email` does a blocking SMTP send inside request handlers while the request's session (and its pooled connection) is still open.

**Performance principle**
Do not hold a scarce shared resource across a slow, unbounded-latency external call.

**Evidence**
- `send_email` sends over SMTP synchronously with no timeout (`utils.py:51`).
- `recover_password` (unauthenticated) queries with the session, then sends before returning (`login.py:54`); `create_user` commits/refreshes then sends (`users.py:57`). The `get_db` session closes only after the response.
- Engine uses default pool settings (`db.py:7`); 4 workers (`Dockerfile`).
- No runtime evidence.

**Impact**
Position: critical path for those endpoints. Frequency: per call. Growth: O(1) per call but holds a connection and thread for the SMTP duration. Blast radius: service (shared pool/threadpool).

**Conditions**
SMTP enabled and slow or unreachable while recovery or user-creation calls arrive concurrently. The recovery endpoint is unauthenticated.

**Counter-evidence**
Email paths are rare and inert when SMTP is unconfigured (`config.py:62`); handlers are threadpool-run so the event loop is not blocked. No BackgroundTasks, queue or SMTP timeout exist.

**Why this might not matter**
With fast SMTP, disabled email and low traffic, hold times are milliseconds.

**Recommendation**
Send via BackgroundTasks (or a queue) and set an SMTP timeout, so the session is released before the external call.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| BackgroundTasks | **preferred** | Smallest change |
| Durable queue + worker | | Only if delivery must survive restarts |
| SMTP timeout only | | Bounds but still holds connection |

**Trade-offs**
Failures are no longer visible to the caller; background tasks are lost on crash.

**Validation**
Pool/connection state and p99 of `/password-recovery` under a stub SMTP that sleeps. Falsifier: latency still tracks SMTP delay after the change.

### PERF-003 — Unbounded `limit`/`skip` on list endpoints

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `backend/app/api/routes/items.py:12` |
| **Tags** | quick-win |

**Problem**
`limit` and `skip` are unconstrained client inputs; each page also runs OFFSET pagination and a `count(*)`.

**Performance principle**
Per-request work must be bounded by the service, not the caller; deep offsets cost O(offset + limit).

**Evidence**
- Plain `int` parameters with no bounds passed to `.offset().limit()` (`items.py:12`); same in `users.py`.
- Whole page is materialised and re-validated per row in Python.
- `count(*)` on every call.

**Impact**
Position: critical path. Frequency: per request. Growth: O(n) in requested rows. Blast radius: service (worker thread, memory).

**Conditions**
A client sends a very large `limit` or deep `skip`, and the caller (or table, for superusers) holds many rows.

**Counter-evidence**
Searched for caps in code, middleware and Traefik config; none. Endpoint is authenticated, which limits who can trigger it.

**Why this might not matter**
Trusted first-party clients with few items never exercise it.

**Recommendation**
`Query(default=100, ge=1, le=<cap>)` and `skip` `ge=0`; keyset pagination if deep paging is expected.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Bound limit/skip | **preferred** | One-line fix |
| Keyset pagination | | Changes API contract |
| Drop per-page count | | Frontend likely needs total |

**Trade-offs**
Clients using very large limits get 422; cap value is a product decision.

**Validation**
Measure latency/peak memory vs `limit=N` on a seeded dataset; add a contract test that over-cap returns 422.

### PERF-004 — Memory-hard hashing on unauthenticated paths without throttling

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Low |
| **Priority** | P3 |
| **Category** | concurrency |
| **Location** | `backend/app/crud.py:45` |
| **Tags** | needs-measurement |

**Problem**
Login and signup hash passwords with Argon2 in the threadpool, including a dummy verification for unknown emails, with no rate limit.

**Performance principle**
CPU/memory-heavy work on an unauthenticated path needs bounded concurrency.

**Evidence**
- Every login attempt verifies a hash, using `DUMMY_HASH` for unknown users (`crud.py:50`).
- `DUMMY_HASH` carries `m=65536,t=3,p=4` in its parameter string (`crud.py:42`); parameters for new hashes come from the library default, not the repo.
- No rate-limiting middleware found. No timing measured.

**Impact**
Position: critical path. Frequency: per login/signup. Growth: O(1) per call. Blast radius: service if concurrent attempts saturate CPU/memory.

**Conditions**
Concurrent login/signup traffic high enough to exhaust container CPU or memory; container limits and live hash cost are unknown.

**Counter-evidence**
Hashing is inherent and the dummy hash is a deliberate timing defence; JWTs mean hashing is not paid per authenticated request (`deps.py:98`). No throttling found.

**Why this might not matter**
Hash cost is intentional; login is a small share of traffic and a proxy rate limit may exist outside the repo.

**Recommendation**
Measure single-hash CPU and RSS in the deployed container; if concurrency can saturate workers, add per-IP/per-account throttling without lowering hash cost.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Measure, then proxy rate limit | **preferred** | Bounds concurrency, keeps security |
| Lower Argon2 cost | | Weakens security; not recommended |

**Trade-offs**
Shared-IP lockouts; in-app limiting adds state.

**Validation**
p95 login latency and peak memory under N concurrent logins in staging; falsifier is flat latency/memory at expected peak.
