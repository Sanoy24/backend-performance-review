## 1. Decision summary

### Overall assessment

A small, conventional FastAPI + SQLModel + PostgreSQL CRUD service with no instrumentation or load tests. The one structural issue worth fixing is a missing index on `item.owner_id`, which sits under the main list endpoint and user deletion. Secondary issues are unbounded page size, slow work (Argon2, SMTP) done while holding a pooled DB connection. All are static findings with no runtime evidence; review confidence is Medium.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add an index on `item(owner_id)` (or composite with `created_at DESC`) via Alembic | Every owner-scoped list/count scans the table; cheap fix |
| 2 | **PERF-002 (P2)** | Add `le=` bound on `limit` and `ge=0` on `skip` | One-line change removes unbounded per-request work |
| 3 | **PERF-003 (P2)** | Release the DB connection before Argon2 verification; set explicit pool sizes | Login is the CPU-heaviest path and shares a default-sized pool |

### Key unknowns

| Unknown | Decision it changes | How to resolve it |
|:--|:--|:--|
| Item table row count and GET /items rate | Severity of PERF-001, PERF-002 | `pg_stat_user_tables` and access logs |
| Login/password-change concurrency, Argon2 time | Whether PERF-003 matters | Hash timing command below; load test |
| Postgres `max_connections`, container CPU limits | Pool sizing for PERF-003 | Deployment config |

### Validation commands

| Finding / unknown | Safety | Command or procedure | Decision it unlocks |
|:--|:--|:--|:--|
| PERF-001 | `safe-on-production` | `SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE relname = 'item';` | If small, downgrade PERF-001 |

## 7. Findings

### PERF-001 — Missing index on item.owner_id

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `backend/app/models.py:87` |
| **Tags** | quick-win, scalability-risk, needs-measurement |

**Problem**
`item.owner_id` is a foreign key with no index, yet every non-superuser GET /items runs a COUNT and an ordered, filtered page query on it, and user deletion deletes items by owner_id.

**Performance principle**
Selective lookups on a growing collection need an access path proportional to the result, not to the table.

**Evidence**
- `models.py:87`: `foreign_key` and `ondelete` only, no `index=True`.
- Migrations create only `ix_user_email` (`e2412789c190_initialize_models.py:33`).
- `items.py:86-98`: filter on `owner_id`, order by `created_at desc`.
- `users.py:398`: `DELETE ... WHERE owner_id`.
- No runtime evidence exists in the repo.

**Impact**
Critical path, per request, O(n) in the item table, service-wide (shared Postgres); two statements per list call (count and page).

**Conditions**
Item table large enough that a full scan is costly (assumed; size unknown) and listing is frequent. Superuser listing is unfiltered and unaffected.

**Counter-evidence**
Searched models, migrations, compose for any index; none. On small tables the planner prefers a sequential scan anyway, which lowers confidence.

**Why this might not matter**
If the table stays in the low thousands of rows, a scan is cheap and the index only adds write cost.

**Recommendation**
Alembic migration adding an index on `item(owner_id)`, ideally composite `(owner_id, created_at DESC)`; declare it in the model.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Composite index | **preferred** | Serves filter, sort, cascade deletes |
| Single-column index | | Removes scan, leaves a sort |
| Cache item lists | | Masks the missing access path, adds invalidation |

**Trade-offs**
Write overhead and storage; use `CREATE INDEX CONCURRENTLY` on a large live table.

**Validation**
Baseline: `EXPLAIN (ANALYZE, BUFFERS)` plan. Expectation: Seq Scan becomes index scan. Falsifier: index already exists or table small. Commands in section 9.

### PERF-002 — Unbounded page size on list endpoints

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `backend/app/api/routes/items.py:72` |
| **Tags** | quick-win |

**Problem**
`skip` and `limit` have no bounds, so one request can read and serialize the whole table; offset pagination rescans skipped rows and a COUNT runs per page.

**Performance principle**
Work per request must be bounded by a server-enforced limit.

**Evidence**
`items.py:72`, `users.py:207` (no `Query(le=...)`); each row validated twice (`items.py:101` and `response_model`). No runtime evidence.

**Impact**
Critical path, per item, O(n), service-level (worker memory and CPU).

**Conditions**
Authenticated client requests a large limit (superuser for /users); matters when the table exceeds what a worker can serialize comfortably. Size unknown.

**Counter-evidence**
No global caps or middleware in repo; proxy config outside repo not checkable. Non-superuser item lists are bounded by the user's own items.

**Why this might not matter**
Requires an authenticated, deliberate client; the bundled frontend uses the default of 100.

**Recommendation**
`Query(ge=1, le=<max>)` on `limit`, `ge=0` on `skip`; consider keyset pagination.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Cap via Query validation | **preferred** | Trivial, removes unbounded work |
| Keyset pagination | | Fixes deep offsets, changes the API |

**Trade-offs**
Clients needing more must page; keyset loses arbitrary page jumps.

**Validation**
Request with large `limit` against seeded data; expect 422 above the cap. Falsifier: another layer already caps it.

### PERF-003 — Argon2 hashing while holding a pooled connection

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/crud.py:47` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Argon2 verification/hashing (CPU and memory heavy) runs in sync handlers while the DB session already holds a connection, on a default-sized pool.

**Performance principle**
Do not hold a scarce shared resource across slow work that does not need it.

**Evidence**
- `crud.py:448`: user query opens a transaction, then `verify_password`; session released at request end.
- `crud.py:444`: dummy hash parameters m=65536,t=3,p=4 (64 MiB, 3 passes per attempt).
- `users.py:280`: `update_password_me` verifies and hashes with a loaded user.
- `db.py:7`: no pool arguments. Derived: 4 x (5+10) = 60 max connections if defaults apply.
- No runtime evidence.

**Impact**
Critical path, per request on login/signup/password change, growth unknown, service-wide via the shared pool.

**Conditions**
Concurrent logins or password changes (login burst, credential stuffing); hash time unmeasured.

**Counter-evidence**
No rate limiting found. Hash cost is deliberate; the issue is its overlap with the held connection. Pool wait not measured, lowering confidence.

**Why this might not matter**
Login is a small share of traffic in most deployments and 60 connections may never be exhausted.

**Recommendation**
Release the transaction before `verify_password`; add login rate limiting; set `pool_size`/`max_overflow`/`pool_timeout` explicitly against Postgres `max_connections`.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Release connection before hashing, explicit pool | **preferred** | Removes the long hold |
| Process pool for hashing | | Complexity before need is measured |

**Trade-offs**
Extra session handling and a second acquisition on the rehash write path; rate limiting adds shared state.

**Validation**
Pool checked-out count and p95 of login under a concurrent load test (not-safe-on-production). Falsifier: negligible pool wait.

### PERF-004 — Synchronous SMTP in request path with no timeout

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | io |
| **Location** | `backend/app/api/routes/login.py:54` |
| **Tags** | needs-measurement |

**Problem**
Password recovery (unauthenticated) and user creation send SMTP mail inline with a DB session open and no explicit SMTP timeout.

**Performance principle**
Do not make user-facing requests wait on a slow external dependency; bound every wait.

**Evidence**
`login.py:58-71` inline `send_email`; `utils.py:45-56` options without timeout; `users.py:243`. No runtime evidence.

**Impact**
Critical path, per request, O(1), service-level through threadpool and connection occupancy.

**Conditions**
SMTP slow or unreachable and recovery requests for registered addresses arrive often enough to occupy the threadpool (assumed).

**Counter-evidence**
No background task or queue found. The `emails` library default timeout was not verified. Mail is only sent if `SMTP_HOST` is set.

**Why this might not matter**
Recovery is rare in most apps and a healthy relay is fast.

**Recommendation**
Explicit SMTP timeout and FastAPI `BackgroundTasks` (or a queue) for sending.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| BackgroundTasks + timeout | **preferred** | Minimal change |
| Dedicated queue/worker | | Heavy for this template |

**Trade-offs**
Failures are not surfaced to the caller; need failure logging.

**Validation**
Latency of the endpoint with a delayed SMTP stub; expect independence from SMTP delay. Falsifier: already independent.
