## 1. Decision summary

### Overall assessment
A small, conventional FastAPI + SQLModel + Postgres CRUD service with sync handlers and no committed measurements. Nothing is likely to fail at small scale. The material issues are a missing index on `item.owner_id`, uncapped pagination, and request-scoped DB connections held across Argon2 hashing and SMTP. Review confidence is Medium: static evidence only, no workload data.

### Top three actions
| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-003 (P2)** | EXPLAIN the item list/count query on realistic data; add a `(owner_id, created_at DESC)` index if it scans | Cost grows with total table size on the hottest endpoint |
| 2 | **PERF-004 (P2)** | Cap `limit` with Query validation | Quick win, bounds per-request memory |
| 3 | **PERF-001 (P2)** | Measure Argon2 time and pool checkout during a login burst; release the session before hashing | Shared pool across all endpoints |

### Key unknowns

|:--|:--|:--|
| Item table size | PERF-003/004 severity | Row counts + EXPLAIN |
| Login/recovery burst rate, pool size | PERF-001/002 relevance | Access logs, runtime pool config |

## 7. Findings

### PERF-001 - Login holds a pooled DB connection across CPU-heavy Argon2 verification

| | |
|:--|:--|
| **Root cause** | ROOT-001 |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/crud.py:45` |
| **Tags** | needs-measurement, scalability-risk |

**Problem**
POST /login/access-token runs the user lookup, then Argon2 verification (and a possible rehash commit) inside a request-scoped Session, so the pooled DB connection stays checked out while the thread burns CPU. The same shape applies to signup, user create, password change and reset.

**Performance principle**
Do not hold a scarce, shared resource (a pooled connection) while doing work that does not need it; CPU-bound work should not occupy a resource whose capacity bounds unrelated requests.

**Evidence**
- get_db yields a Session for the whole request; a SELECT starts a transaction and the connection is held until the session closes. (`backend/app/api/deps.py:20`)
- authenticate does get_user_by_email, then verify_password (Argon2 with bcrypt fallback) before returning; the not-found branch also verifies against a DUMMY_HASH with m=65536,t=3,p=4, so every login attempt (valid or not) pays the hash cost. (`backend/app/crud.py:45`)
- Engine is created with no pool arguments, so pool size/overflow/timeout are library defaults, and the route handlers are sync def (run in the framework threadpool). (`backend/app/core/db.py:7`)
- Same pattern: update_password_me verifies then hashes with the session open; create_user hashes after get_user_by_email. (`backend/app/api/routes/users.py:110`)
- Dockerfile runs 4 workers, so pool capacity is per-process. (`backend/Dockerfile`)
- No runtime evidence exists (no profile, load test or EXPLAIN in the repo).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters only if concurrent login/signup/password operations approach the per-process pool size (assumed to be the SQLAlchemy default, not set in the repo) while other endpoints also need connections; e.g. a login burst or credential-stuffing traffic. Negligible at low auth rates. Argon2 hashing time on the deployment CPU is unmeasured.

**Counter-evidence**
- Looked for an explicit pool configuration or a separate hashing executor; none exists. [no-effect]
- Hashing runs in a threadpool thread (sync def), so it does not block the event loop; impact is pool/CPU occupancy, not loop stall. [bounds-impact]
- Argon2 is a deliberate cost; the fix must not weaken the hash parameters. [bounds-impact]

**Why this might not matter**
At typical template-scale login rates the pool is rarely contended, and CPU may saturate well before the pool does. If DB connections are not the limiting resource, the connection hold is a minor second-order effect.

**Recommendation**
Release the connection before hashing in credential paths: read the user row, end the transaction (commit/close or a short-lived session for the lookup), verify the hash, then reopen only to persist a rehash. Pair with explicit pool settings and a rate limit on the login endpoint sized from measurement.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Short-lived session for the lookup, hash outside it | **preferred** | Removes the overlap directly; no new components. |
| Raise pool_size/max_overflow |  | Masks the overlap and shifts pressure to Postgres max_connections across 4 workers. |
| Rate-limit login |  | Useful for abuse, but does not fix the hold on legitimate bursts. |

**Trade-offs**
Slightly more session handling code in the auth path; a rehash needs a second short transaction. Raising pool size would cost DB memory per connection.

**Validation**
Metric: Peak checked-out connections (engine.pool.checkedout()) and p95 of a non-auth endpoint while a login burst runs. Expectation: Checked-out connections during hashing drop toward zero for login requests; direction only, magnitude unmeasured. Falsifier: Pool checked-out count stays far below capacity during a realistic login burst, or CPU saturates first. Safety: not-safe-on-production. Guard: A load-test case mixing POST /login/access-token with GET /items/ in staging.
- `not-safe-on-production` `python -c "import time;from app.core.security import get_password_hash,verify_password;h=get_password_hash('x'*12);t=time.perf_counter();verify_password('x'*12,h);print(time.perf_counter()-t)"` - Measure one Argon2 verification on the target hardware (run from backend/ in a staging environment).

### PERF-002 - Synchronous SMTP send inside request handlers holds a worker thread and DB session

| | |
|:--|:--|
| **Root cause** | ROOT-001 |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | io |
| **Location** | `backend/app/api/routes/users.py:73` |
| **Tags** | needs-measurement |

**Problem**
create_user and recover_password call send_email inline; the SMTP round trip (connect, TLS, auth, send) blocks the request thread and keeps the Session/connection open until it finishes.

**Performance principle**
Side effects with unbounded external latency should not sit on the response path or hold shared resources; their latency is independent of local capacity.

**Evidence**
- send_email builds a message and calls message.send(...) synchronously; no timeout is passed in smtp_options (host, port, tls, user, password only). (`backend/app/utils.py:46`)
- Called inline in create_user after crud.create_user, with the session dependency still open. (`backend/app/api/routes/users.py:73`)
- recover_password does the user lookup, then sends the email inline before returning. (`backend/app/api/routes/login.py:67`)
- No runtime evidence exists (no profile, load test or EXPLAIN in the repo).

**Impact**
Position: critical-path; frequency: per-request; growth: O(1); blast radius: endpoint.

**Conditions**
Applies only when SMTP is configured (emails_enabled requires SMTP_HOST and EMAILS_FROM_EMAIL, config.py:61). Matters if the SMTP server is slow or degraded or if password-recovery requests arrive in bursts; /password-recovery/{email} is unauthenticated, so burst volume is not controlled by the operator. SMTP latency is unmeasured.

**Counter-evidence**
- Looked for a background task, queue or timeout around send_email; none found. [no-effect]
- Emails are only sent when SMTP is configured, and user creation is an admin action, bounding create_user exposure. [bounds-impact]

**Why this might not matter**
User creation is superuser-only and password recovery is low-volume in most deployments; a few slow sends are tolerable in the threadpool. The unauthenticated recovery endpoint is the only place burst traffic is plausible.

**Recommendation**
Move email delivery off the response path (background task or queue worker) after committing, and set an explicit SMTP timeout. Do the DB work first and release the session before the network call.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Background task after commit plus explicit SMTP timeout | **preferred** | Smallest change that removes SMTP latency from the response and bounds a hung server. |
| External queue/worker |  | More robust delivery and retries, but adds infrastructure unjustified without volume data. |
| Only add a timeout |  | Bounds worst case but leaves latency on the path. |

**Trade-offs**
Delivery failures become asynchronous and need logging/retry policy; background tasks are lost on worker crash.

**Validation**
Metric: Latency of POST /password-recovery/{email} and POST /users/ with SMTP pointed at a deliberately slow test server. Expectation: Response time decouples from SMTP latency after the change (direction only). Falsifier: Response time is unchanged by SMTP delay, meaning the send is not on the path. Safety: not-safe-on-production. Guard: Test asserting the handler returns while a mocked send_email blocks.

### PERF-003 - No index on item.owner_id or item.created_at; list, count and delete scan the item table

| | |
|:--|:--|
| **Root cause** | ROOT-002 |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `backend/app/models.py:97` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Item.owner_id (a foreign key) and created_at are not indexed. GET /items/ filters by owner_id, counts, and orders by created_at desc; Postgres does not index foreign keys automatically, so each call can read the whole table. The owner cascade delete has the same lookup.

**Performance principle**
Access paths must exist for the predicates and orderings on the hot path; otherwise per-request cost grows with total table size rather than result size.

**Evidence**
- owner_id is declared with foreign_key and ondelete only, no index=True; created_at has no index. (`backend/app/models.py:97`)
- The only create_index in all migrations is ix_user_email on user.email. (`backend/app/alembic/versions/e2412789c190_initialize_models.py:33`)
- Per request, read_items runs a count with WHERE owner_id and a SELECT with WHERE owner_id ORDER BY created_at DESC OFFSET/LIMIT; superusers count and sort the entire table. (`backend/app/api/routes/items.py:14`)
- delete_user issues DELETE FROM item WHERE owner_id before deleting the user. (`backend/app/api/routes/users.py:237`)
- No runtime evidence exists (no profile, load test or EXPLAIN in the repo).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters when the item table is large enough that scanning it dominates (row count unknown). Per-request cost grows with total items across all users, and the shared DB serves every endpoint.

**Counter-evidence**
- Looked for index definitions in models, migrations and elsewhere; only user.email is indexed. [no-effect]
- The planner may choose a seq scan efficiently on small tables; no EXPLAIN is available. [lowers-confidence]

**Why this might not matter**
If the item table stays in the thousands of rows, a sequential scan is fast and an extra index adds write cost for no benefit. Row counts are unknown.

**Recommendation**
After confirming with EXPLAIN on realistic data, add a composite index on (owner_id, created_at DESC) via an Alembic migration (it also serves the per-user count and the cascade delete). Superuser global listing may additionally need an index on created_at.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Composite (owner_id, created_at DESC) index | **preferred** | One index serves filter, order and cascade lookup. |
| Single-column owner_id index |  | Fixes the filter but leaves a sort step. |
| Do nothing until table size is known |  | Reasonable if volume is small; see validation. |

**Trade-offs**
Extra write cost and storage on item inserts; creating the index on a populated table needs CREATE INDEX CONCURRENTLY to avoid write locks.

**Validation**
Metric: EXPLAIN (ANALYZE, BUFFERS) of the list and count queries for a user on a representative item table. Expectation: Seq Scan on item becomes an index scan; buffers read fall (direction only). Falsifier: The planner already uses a fast plan at the real row count, or the table is small. Safety: not-safe-on-production. Guard: Slow-query alert on the item list query.
- `not-safe-on-production` `EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM item WHERE owner_id = '<uuid>' ORDER BY created_at DESC OFFSET 0 LIMIT 100;` - Show the access path for the list query (run on staging with realistic data).

### PERF-004 - Pagination limit is caller-controlled and uncapped; offset pagination plus per-row double validation

| | |
|:--|:--|
| **Root cause** | ROOT-003 |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `backend/app/api/routes/items.py:15` |
| **Tags** | quick-win |

**Problem**
GET /items/ and GET /users/ accept skip and limit as plain ints with no maximum or lower bound, so a single request can ask for every row, all materialized as ORM objects, validated into public models, then serialized. skip uses OFFSET, which reads and discards skipped rows.

**Performance principle**
Bound the work and memory one request can demand; per-request cost should be capped independent of caller input and dataset size.

**Evidence**
- limit: int = 100 and skip: int = 0 with no Query constraint; the statement uses .offset(skip).limit(limit) and .all(). (`backend/app/api/routes/items.py:15`)
- Each row is validated again via ItemPublic.model_validate and wrapped in ItemsPublic, then response_model validates/serializes it again. (`backend/app/api/routes/items.py:39`)
- Same pattern for users. (`backend/app/api/routes/users.py:37`)
- No runtime evidence exists (no profile, load test or EXPLAIN in the repo).

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: endpoint.

**Conditions**
Any authenticated user can set limit large; non-superusers are bounded by their own item count, superusers (and /users/, superuser-only) by the whole table. Matters once tables hold many thousands of rows or a client misbehaves; memory is per worker process (4 workers).

**Counter-evidence**
- Looked for a global cap, middleware, or Query validation; none found. [no-effect]
- Non-superuser exposure is limited to the caller's own rows, and /users/ requires superuser. [bounds-impact]

**Why this might not matter**
Callers are mostly the template's own frontend using its default page size; abuse needs a valid token, and per-user datasets may be small.

**Recommendation**
Constrain limit (Query with ge=1 and a chosen le cap) and skip ge=0, and drop the redundant model_validate pass by returning ORM rows to response_model. Consider keyset pagination on (created_at, id) if deep paging is expected.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Cap limit with Query validation | **preferred** | One-line, removes the unbounded case. |
| Keyset pagination |  | Fixes deep-offset cost but changes the API contract; only worth it if deep paging is real. |
| Leave as is |  | Acceptable only if all callers are trusted. |

**Trade-offs**
Clients requesting more than the cap must page; the cap value is a product decision.

**Validation**
Metric: Response time and peak worker RSS for GET /items/ with a large limit against a seeded table. Expectation: Requests above the cap are rejected (422) or clamped; direction only. Falsifier: A proxy-level cap already exists, or memory/latency stays flat as limit grows. Safety: not-safe-on-production. Guard: API test asserting limit above the cap returns 422.
