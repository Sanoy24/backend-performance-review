## 1. Decision summary

### Overall assessment

A small, conventional FastAPI + SQLModel + PostgreSQL CRUD service. There are no N+1 patterns, no blocking calls in `async def` handlers, and no heavy startup work. The one structural problem worth acting on is a missing index on `item.owner_id`, which sits under the main list endpoint, the count and the cascade delete. Two further risks (inline SMTP and Argon2 hashing while holding a DB session) depend on traffic and deployment facts the repository does not state. Review confidence is Medium: static only, no runtime evidence, no committed measurements.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add a migration for an index on `item(owner_id, created_at DESC)`. | High confidence from code; cheap; grows linearly with data. |
| 2 | **PERF-002 (P2)** | Set an SMTP timeout and send email via background task. | Removes dependency tail latency and DB-connection hold from request path. |
| 3 | **PERF-004 (P2)** | Add login rate limiting and release the DB session before hashing. | Unauthenticated callers control a memory-hard hashing rate. |

## 3. Architecture overview

Single backend service: `fastapi run --workers 4` (`backend/Dockerfile`), behind Traefik, talking to one PostgreSQL instance. The SQLAlchemy engine uses library defaults (`backend/app/core/db.py:6`). Every route except `health_check` is a sync `def`, so FastAPI runs it in a threadpool. A session is created per request through a `yield` dependency (`backend/app/api/deps.py:21`) and stays open until the response is complete. Each authenticated request does one primary-key user lookup.

## 7. Findings

### PERF-001 — Items list queries have no index on owner_id

ID: PERF-001 | Root cause: ROOT-001 | Severity: High | Confidence: High | Priority: P1 | Category: data-access | Location: `backend/app/api/routes/items.py:14` (`read_items`) | Tags: quick-win, scalability-risk

**Problem.** `GET /items/` runs `count(*)` and a filtered, `ORDER BY created_at DESC`, offset/limit select on `item.owner_id`. `owner_id` is a foreign key without `index=True` (`backend/app/models.py:97`) and no migration creates an index on `item` (the only `create_index` is `ix_user_email`, `e2412789c190_initialize_models.py:33`). PostgreSQL does not index FK referencing columns automatically (general database fact, not in the repo).

**Performance principle.** Work per request should be proportional to the result, not to the whole data set.

**Evidence.** Static only: `items.py:29-42`, `models.py:97`, migration directory. No runtime evidence is committed.

**Impact.** Critical path, per request, O(n) in item-table size, 2 queries per call (count and page), service-wide because the scan competes for shared DB resources. The same column is probed by the ON DELETE CASCADE and by `delete_user`'s bulk delete.

**Conditions.** Once the table is large enough that a sequential scan is measurably slower than an index lookup; the size is unknown (assumption, not read from the repo).

**Counter-evidence.** On small tables a seq scan is fast, and the planner may choose it anyway. Searched for any index on `item`: none.

**Why this might not matter.** If deployments hold a few thousand items total, the index adds write cost for no visible benefit.

**Recommendation.** Migration adding a btree index on `item(owner_id, created_at DESC)`.

**Alternatives.** Index on `owner_id` only (leaves a sort); caching the count (adds invalidation, does not fix the page query). Preferred: composite index.

**Trade-offs.** Index storage, slightly slower item writes; build concurrently on a large table.

**Validation.** Metric: plan node type and time for list and count queries. Expect Seq Scan to become an index scan. Falsifier: staging EXPLAIN already acceptable and unchanged after the index. Commands in section 9.

#### PERF-002 — Inline SMTP in request path

Medium / Medium / P2, networking. `recover_password` (`login.py:67`), `create_user` (`users.py:73`) and `test_email` (`utils.py:21`) call `send_email` synchronously. `send_email` sets no timeout (`utils.py:46-55`), and the yield-dependency session (`deps.py:21`) keeps a pooled connection checked out during the send. Conditions: email enabled in production and a slow or unreachable SMTP host; `/password-recovery/{email}` is unauthenticated so its rate is client-controlled. Counter-evidence: low-traffic endpoints; sync handlers use the threadpool so the event loop is not blocked; recovery only sends for existing users. Why it might not matter: email disabled or fast provider. Recommendation: explicit SMTP timeout plus FastAPI BackgroundTasks (queue only if delivery guarantees are needed). Alternatives: timeout only (still holds the request); external queue (operational burden unjustified without volume). Trade-offs: no delivery error to caller; lost on crash. Validation: p95 of the endpoint against a delayed SMTP stub (safe-on-production), falsified if latency is unchanged after the change or the library already enforces a short timeout.

#### PERF-004 — Memory-hard hashing on every login attempt inside an open DB session

Medium / Medium / P2, concurrency, tags needs-measurement. `authenticate` (`crud.py:45-60`) verifies against the real hash, or against `DUMMY_HASH` for unknown users, so each attempt costs a full Argon2 verification (the encoded parameters are m=65536, t=3, p=4, `crud.py:41`). It runs in a sync handler with the session open, under 4 workers, and the repo has no login throttling (nothing in app code or Traefik labels in `compose.yml`). The same hashing is used for signup, user create/update and password change. Conditions: concurrent logins or credential-stuffing; login rate and container limits unknown, so no per-hash cost is asserted. Counter-evidence: the cost is a deliberate security choice and the threadpool keeps the event loop free. Why it might not matter: low login volume with a rate-limiting proxy in front. Recommendation: do not weaken the hash; release the DB session before verifying, add login rate limiting, and size worker memory for concurrent hashes. Alternative: lower Argon2 cost (rejected: trades security for speed without measurements). Trade-offs: shared-IP lockouts; slight restructure of session lifetime. Validation: login p95, worker CPU/RSS and checked-out connections under concurrent logins (not-safe-on-production); falsified if a realistic-concurrency load test is flat.

#### PERF-003 — Unbounded page size on list endpoints

Low / High / P3, serialization, quick-win. `limit: int = 100` has no maximum in `users.py:37` or `items.py:15`; all rows are validated into Pydantic models and returned in one response, plus a count per call. Users listing is superuser-only and items are scoped to the caller, which bounds impact. Recommendation: `Query(100, ge=1, le=<cap>)`, `skip ge=0`, keyset pagination if deep paging is expected. Trade-off: API behaviour change for callers requesting more than the cap.
