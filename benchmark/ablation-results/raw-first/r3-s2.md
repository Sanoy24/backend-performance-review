Review confidence is Medium: everything is derived from source, and table sizes and traffic are unknown.

## 3. Findings

### PERF-001 — Missing index for per-owner item listing (High / High / P1)

- **Category:** data-access. **Location:** `backend/app/models.py:97` (`Item`). **Tags:** quick-win, scalability-risk.
- **Problem:** `item.owner_id` and `item.created_at` have no index. `GET /items/` filters by owner, counts, and sorts by `created_at` on every call.
- **Principle:** Work per request should scale with result size, not total data size.
- **Evidence:** `Item.owner_id` has only `foreign_key`/`ondelete` (`models.py:97`); `read_items` issues `COUNT(*)` and an ordered, paged `SELECT` (`items.py:19-40`); the only index created by migrations is `ix_user_email` (`e2412789c190...py:33`). PostgreSQL does not index FK columns automatically. No runtime evidence exists.
- **Impact:** Critical path, per request, O(n) in table size, endpoint blast radius. The same column drives the cascade/explicit delete of a user's items.
- **Conditions:** Matters when the item table is large enough for a scan to dominate; size unknown.
- **Counter-evidence:** No index found in any migration; an out-of-band index would not be visible. LIMIT bounds the result, not the scan.
- **Why this might not matter:** For a few thousand rows a sequential scan is cheap.
- **Recommendation:** Alembic migration adding a composite index `(owner_id, created_at DESC)` and declaring it in the model.
- **Alternatives:** Single-column `owner_id` index (still sorts per user); caching list responses (masks the scan, adds invalidation). Preferred: composite index.
- **Trade-offs:** Index storage, slightly slower writes; use `CREATE INDEX CONCURRENTLY` on a large table.
- **Validation:** `EXPLAIN (ANALYZE, BUFFERS)` shows Seq Scan replaced by an index scan (not-safe-on-production; use staging). Falsifier: plan already uses an index.

### PERF-003 — Unbounded page size, OFFSET pagination, per-call COUNT (Medium / High / P2)

- **Category:** data-access. **Location:** `backend/app/api/routes/items.py:14` (`read_items`); same in `users.py:32`. **Tags:** quick-win.
- **Problem:** `limit` and `skip` are unconstrained ints; rows are fully materialised with `.all()`, re-validated per item, then serialised again.
- **Principle:** Bound the work any single request can demand.
- **Evidence:** `items.py:15`, `items.py:42`, `users.py:32`.
- **Impact:** Critical path, per request, O(n) in requested rows, service-level memory/CPU pressure.
- **Conditions:** An authenticated caller (or buggy client) requests a large limit against a large table; default 100 is bounded.
- **Counter-evidence:** Authentication required; non-superusers see only their own rows.
- **Why this might not matter:** Abuse requires deliberate action and authenticated access.
- **Recommendation:** `Query(ge=1, le=<max>)` on `limit`, `ge=0` on `skip`; consider keyset pagination.
- **Alternatives:** Keyset pagination (changes the API contract). Preferred: cap.
- **Trade-offs:** Clients wanting more must page.
- **Validation:** Large-limit request is rejected or clamped; RSS per request bounded (not-safe-on-production).

### PERF-002 — DB connection held across Argon2 hashing in login (Medium / Medium / P2)

- **Category:** concurrency. **Location:** `backend/app/api/routes/login.py:23` (`login_access_token`). **Tags:** scalability-risk, needs-measurement.
- **Problem:** `authenticate` queries via the request session (connection checked out), then runs Argon2 verification while still holding it; unknown-user logins also hash against `DUMMY_HASH`.
- **Principle:** Do not hold a scarce shared resource across slow unrelated work.
- **Evidence:** `crud.py:54-63`; Argon2 first in `security.py:12` (dummy hash parameters m=65536, t=3, p=4 per the committed string); `create_engine` with default pool (`core/db.py:6`); 4 workers (`Dockerfile`).
- **Impact:** Critical path, per login request, O(1) per request, service blast radius if logins burst.
- **Conditions:** Bursts of concurrent logins or credential stuffing; hash latency, pool size, and traffic are not measured.
- **Counter-evidence:** Sync handlers run in the threadpool so the event loop is not blocked; no login rate limiting found.
- **Why this might not matter:** Logins are infrequent for most apps and hashing cost is the intended security property.
- **Recommendation:** Read the user, end the transaction, then verify; bound concurrent hashes or rate limit login; size the pool against threads.
- **Alternatives:** Lower Argon2 cost (weakens security); proxy rate limit (does not shorten hold time). Preferred: release before hashing.
- **Trade-offs:** More auth-path code; rehash write needs a fresh session.
- **Validation:** Pool checkout counts and p95 login latency under concurrent logins (not-safe-on-production). Falsifier: flat latency and low pool use under load.

### PERF-004 — Inline SMTP while holding a DB session (Low / Medium / P3)

- **Category:** io. **Location:** `backend/app/api/routes/login.py:55` (`recover_password`). **Tags:** needs-measurement.
- **Problem:** `send_email` runs synchronously in the request, after a user lookup, with no explicit SMTP timeout (`utils.py:46`); also in `create_user` and `test_email`.
- **Principle:** Keep slow external I/O off the request path.
- **Impact:** Critical path but rare; endpoint blast radius.
- **Conditions:** Slow or unreachable SMTP, or high-rate hits to the unauthenticated recovery endpoint; emails require SMTP configuration.
- **Counter-evidence:** Default timeout of the mail library not verified; low frequency.
- **Recommendation:** Use `BackgroundTasks` (or a queue) and set an explicit SMTP timeout.
- **Trade-offs:** Post-response failures need logging; tasks are lost on crash.
- **Validation:** p95 latency of `POST /password-recovery/{email}` with a delayed SMTP stub should become independent of SMTP delay (not-safe-on-production).
