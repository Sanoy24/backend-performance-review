## 7. Findings

### PERF-001 - No index on item.owner_id behind the main list endpoint

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `backend/app/models.py:97` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Item.owner_id is a foreign key with no index, yet GET /items/ filters by it twice per request (COUNT and the page query) and orders by created_at; deleting a user also cascades through it.

**Performance principle**
A lookup that selects a small subset of a growing table must be answered by an access path proportional to the result, not to the table.

**Evidence** (no runtime evidence exists)

- Item.owner_id is declared with foreign_key and ondelete only; no index=True. (`backend/app/models.py:97`)
- read_items runs COUNT(*) WHERE owner_id = :id, then SELECT ... WHERE owner_id = :id ORDER BY created_at DESC OFFSET/LIMIT, on every list call for non-superusers. (`backend/app/api/routes/items.py:29`)
- The only create_index in migrations is ix_user_email; no migration indexes item.owner_id or item.created_at. (`backend/app/alembic/versions/e2412789c190_initialize_models.py:33`)
- Superuser path has no WHERE and orders by created_at with no index on that column. (`backend/app/api/routes/items.py:21`)
- No runtime evidence (EXPLAIN, slow-query log) is committed. Planner behaviour is inferred from the absence of an index; PostgreSQL does not create indexes for FK columns automatically.

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters once the item table is large relative to a single owner's items (sequential-scan cost scales with total rows, not the owner's rows). Row counts are unknown; assumed the item table grows with user count. Negligible for a small table.

**Counter-evidence**

- Looked for an index on item.owner_id in models and all five migrations; none found. (effect: no-effect)
- Table size is unknown; a small table makes a seq scan cheap. Confidence capped at Medium for that reason. (effect: lowers-confidence)

**Why this might not matter**
If the item table stays in the low thousands of rows, a sequential scan is cheap and the index adds write cost for little read gain. This is a template; many deployments never reach the scale where it matters.

**Recommendation**
Add a composite index on item (owner_id, created_at) via an Alembic migration (Field(index=True) on owner_id at minimum). It serves the filter, the COUNT, the ordered page, and the FK cascade lookup on user delete.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Composite index (owner_id, created_at) | **preferred** | One structure serves filter and sort; avoids a sort step. |
| Single-column index on owner_id |  | Fixes the filter but leaves a sort of the owner's rows. |
| Cache list responses |  | Masks the scan, adds invalidation; not justified without a measured hit rate. |

**Trade-offs**
Extra write cost and storage on item inserts/updates; building the index on a large table needs CREATE INDEX CONCURRENTLY outside a transaction to avoid blocking writes.

**Validation**
Metric: EXPLAIN (ANALYZE, BUFFERS) plan node type and time for the items list query for a user with few items in a large item table. Expectation: Seq Scan on item replaced by an index scan; time depends on the owner's item count rather than table size. Falsifier: Plan already uses an index or the table is small enough that scan time is negligible. Safety: not-safe-on-production.

### PERF-002 - Login holds a DB connection across Argon2 hashing

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/api/routes/login.py:24` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
login_access_token (sync def) looks up the user, which opens a transaction on a pooled connection, then runs an Argon2 verify (and a dummy verify for unknown emails) before the session closes. The connection and a worker thread are held across CPU-heavy hashing; no pool or concurrency configuration exists.

**Performance principle**
Do not hold a scarce shared resource (pooled connection) across CPU-bound work that does not need it, and bound concurrency of expensive work.

**Evidence** (no runtime evidence exists)

- authenticate queries by email then calls verify_password before returning; the session from get_db stays open for the whole request. (`backend/app/crud.py:45`)
- DUMMY_HASH is an Argon2id hash encoding m=65536,t=3,p=4 (64 MiB memory parameter), so unknown-email attempts cost the same as real ones. (`backend/app/crud.py:43`)
- create_engine is called with only the URL; no pool_size, max_overflow or pool_timeout are set, so library defaults apply. (`backend/app/core/db.py:5`)
- The container runs 4 workers; each has its own pool and thread pool. (`backend/Dockerfile:52`)
- get_db yields a Session for the whole request. (`backend/app/api/deps.py:20`)
- No rate limit or concurrency cap on /login/access-token; no runtime measurements committed.

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
A burst of concurrent logins (or failed-login attempts) larger than the per-worker connection pool default; each in-flight verify holds a connection for its CPU time, so other endpoints can queue on the pool. Login rate and hash cost on the deployed CPU are unknown.

**Counter-evidence**

- Checked whether the session is released before hashing; it is not, as get_db wraps the whole request. (effect: no-effect)
- Argon2 verify latency is unmeasured, so impact is a risk, not a measurement. (effect: lowers-confidence)

**Why this might not matter**
Most deployments see low login rates, and Argon2 cost is intentional for security. If logins are rare the pool is never contended.

**Recommendation**
Release the DB connection before hashing: fetch the user, copy hashed_password, end the transaction, verify, then write the rehash only when needed. Consider a bounded concurrency limit on hashing and set pool_size/pool_timeout explicitly from worker and thread counts.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Release connection before verify; bound hash concurrency | **preferred** | Removes the shared-resource hold without weakening hashing. |
| Lower Argon2 cost |  | Weakens security; trades away the intended property. |
| Enlarge the pool |  | Raises database connection load and masks the hold. |

**Trade-offs**
Slightly more code in authenticate; a concurrency cap adds queueing latency at login under bursts.

**Validation**
Metric: SQLAlchemy pool checked-out count and p95 latency of a concurrent endpoint (e.g. GET /items/) while a login burst runs. Expectation: Pool checkout wait during login bursts drops after the connection is released before hashing. Falsifier: Pool never nears exhaustion in a burst test at the expected login rate. Safety: not-safe-on-production.

### PERF-003 - Synchronous SMTP delivery inside request handlers

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | io |
| **Location** | `backend/app/utils.py:33` |
| **Tags** | scalability-risk |

**Problem**
send_email performs a blocking SMTP exchange (emails library message.send) inline in POST /password-recovery/{email} and POST /users/. The request, its worker thread and its session wait for the mail server.

**Performance principle**
Keep slow, failure-prone external I/O off the user-blocking path or bound it with a deadline.

**Evidence** (no runtime evidence exists)

- message.send is called synchronously; smtp_options holds host, port, tls/ssl and credentials only; no timeout key is set. (`backend/app/utils.py:46`)
- recover_password calls send_email directly after a DB lookup, so the session stays open during delivery. The endpoint is unauthenticated and sends only for existing users. (`backend/app/api/routes/login.py:54`)
- create_user also sends inline. (`backend/app/api/routes/users.py:69`)
- No background task, queue or worker exists in the repository.

**Impact**
Position: critical-path; frequency: per-request; growth: O(1); blast radius: service.

**Conditions**
Applies only when emails are enabled and the SMTP server is slow or unreachable; a degraded mail server then ties up worker threads and pooled connections in proportion to concurrent recovery requests. Whether the emails library applies a default socket timeout is not verified here.

**Counter-evidence**

- Looked for BackgroundTasks, queues or timeouts; none found. (effect: no-effect)
- Volume on these endpoints is expected to be low; impact depends on unmeasured mail-server health. (effect: bounds-impact)

**Why this might not matter**
These endpoints are low-volume and mail is usually fast; a template deployment may never degrade. Moving to async delivery changes error semantics.

**Recommendation**
Run delivery via FastAPI BackgroundTasks (or an external queue if durability matters) after the response, and set an explicit SMTP timeout.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| BackgroundTasks plus explicit SMTP timeout | **preferred** | Smallest change that takes mail off the response path. |
| Durable queue and worker |  | Heavier; only justified if delivery loss is unacceptable. |

**Trade-offs**
Failures are no longer returned to the caller; background tasks are lost on process restart.

**Validation**
Metric: Latency of POST /password-recovery/{email} against an SMTP sink with injected delay. Expectation: Response latency independent of SMTP latency after the change. Falsifier: Latency is already independent of SMTP delay, e.g. the library imposes a short timeout. Safety: not-safe-on-production.

### PERF-004 - Unbounded limit and OFFSET pagination on list endpoints

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | serialization |
| **Location** | `backend/app/api/routes/items.py:15` |
| **Tags** | quick-win |

**Problem**
skip and limit are plain int parameters with no upper bound on /items/ and /users/. A caller can request an arbitrarily large page, materialised as ORM objects, revalidated into Pydantic models and serialised in one response. Every page also issues a separate COUNT(*).

**Performance principle**
Bound the work and memory any single request can demand.

**Evidence** (no runtime evidence exists)

- limit: int = 100 with no le= constraint; no maximum is enforced. (`backend/app/api/routes/items.py:15`)
- Same signature on read_users. (`backend/app/api/routes/users.py:37`)
- session.exec(statement).all() then a list comprehension of ItemPublic.model_validate builds the whole page in memory. (`backend/app/api/routes/items.py:44`)
- Each call issues COUNT(*) plus the OFFSET query (two statements). (`backend/app/api/routes/items.py:23`)

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: service.

**Conditions**
A single authenticated caller with a large owned dataset (a superuser sees all items) requesting a very large limit; memory and CPU scale with the page size the client chooses. Request frequency and data volume are unknown.

**Counter-evidence**

- Searched for a Query(le=...) cap or middleware limit; none in the repository (reverse proxy config not examined for body limits). (effect: no-effect)

**Why this might not matter**
Only authenticated users can call it and the default is 100; abuse needs a legitimate account holding many rows.

**Recommendation**
Constrain with Query(100, ge=1, le=<chosen max>) and ge=0 on skip; consider keyset pagination on (created_at, id) if deep paging is expected.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Cap limit with Query validation | **preferred** | One-line fix addressing the unbounded work. |
| Keyset pagination |  | Removes OFFSET cost but changes the API contract. |

**Trade-offs**
Clients requesting larger pages receive a 422 and must page.

**Validation**
Metric: Peak process memory and response time for GET /items/?limit=<large> against a seeded dataset. Expectation: Requests above the cap are rejected before touching the database. Falsifier: Large-limit requests are already rejected or memory use is flat. Safety: not-safe-on-production.
