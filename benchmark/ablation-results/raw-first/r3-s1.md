## 1. Decision summary

### Overall assessment

A small, conventional FastAPI + SQLModel + PostgreSQL CRUD service with no N+1 patterns and no event-loop blocking. Four moderate issues were found, all from static reading with no runtime evidence: a missing index behind the per-user item list (PERF-001), unbounded page size (PERF-002), CPU-heavy hashing and slow SMTP on shared request resources (PERF-003, PERF-004). Review confidence is Medium; the repository has no metrics, load tests or query plans.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add an Alembic migration for an index on `item (owner_id, created_at DESC)` after checking a query plan | Hot list endpoint scans scale with total table size |
| 2 | **PERF-002 (P2)** | Cap `limit` and require `skip >= 0` on list endpoints | One-line, removes caller-controlled work |
| 3 | **PERF-004 (P2)** | Send email after releasing the DB session, in a background task with an SMTP timeout | Unauthenticated endpoint holds a connection during external I/O |

### Key unknowns

| Login/signup burst rate and hash time | Whether PERF-003 needs more than proxy rate limiting | Hash timing and thread-pool occupancy under load |

## 7. Findings

### PERF-001 — Unindexed `item.owner_id` behind the per-user item list

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `backend/app/models.py:97` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
Every non-superuser `GET /items/` runs `COUNT(*)` and an `ORDER BY created_at DESC OFFSET/LIMIT` query filtered on `owner_id`, but no index covers `owner_id` or `created_at`.

**Performance principle**
Lookups on a selective predicate need an access path on that key; otherwise work scales with total data rather than result size.

**Evidence**
- `owner_id` has `foreign_key`/`ondelete` only, no `index=True` (`backend/app/models.py:97`), while `User.email` does.
- Only `ix_user_email` is created in migrations (`backend/app/alembic/versions/e2412789c190_initialize_models.py:33`).
- Queries at `backend/app/api/routes/items.py:32-48`.
- PostgreSQL does not auto-index foreign keys (general knowledge, not stated in the repo).
- No runtime evidence exists in the repository.

**Impact**
Position: critical path. Frequency: per request. Growth: O(n) in total item rows. Blast radius: service (scans contend for shared DB I/O).

**Conditions**
Material when the item table is large (assumed to grow with usage). Negligible at a few thousand rows. The superuser path sorts without an index, and cascade deletes must locate items by `owner_id`.

**Counter-evidence**
No index found in models or migrations (no effect). Table size unknown (lowers confidence).

**Why this might not matter**
If the deployment holds few items, the scan is cheap and the index adds write cost for nothing.

**Recommendation**
Add composite index `item (owner_id, created_at DESC)` through Alembic, created concurrently on a populated table.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Composite `(owner_id, created_at DESC)` | **preferred** | Covers filter and ordering |
| Single-column `owner_id` | | Still sorts per owner |
| Keyset pagination only | | Does not remove the scan |

**Trade-offs**
Extra write cost and storage; index build time on large tables.

**Validation**
Baseline plan with EXPLAIN on a staging copy (`not-safe-on-production`, ANALYZE executes the query). Expect Seq Scan to become Index Scan. Falsifier: planner already uses an index or table is small.

### PERF-002 — Unbounded `skip`/`limit` on list endpoints

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `backend/app/api/routes/items.py:15` |
| **Tags** | quick-win |

**Problem**
`limit` and `skip` have no bounds; a caller can request an arbitrarily large page, which is fully loaded and validated twice (`model_validate` per row, then `response_model`).

**Performance principle**
Per-request work must be bounded by the server, not caller-chosen parameters.

**Evidence**
`items.py:15` (no `le`/`ge`), `items.py:42` (per-row validation), `users.py:37` (same pattern). No runtime evidence.

**Impact**
Critical path, per item, O(n) in requested page size, endpoint-level (memory and CPU in a worker).

**Conditions**
Matters when a user or the superuser has far more rows than the default page or passes a large limit/offset. Requires authentication.

**Counter-evidence**
No page-size cap in app or compose config (no effect). Authentication required (bounds impact).

**Why this might not matter**
Rows are small and callers authenticated; practical cost may be modest.

**Recommendation**
Add `Query(100, ge=1, le=<cap>)` for `limit`, `ge=0` for `skip`; consider keyset pagination; remove the redundant manual validation.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Server-side cap | **preferred** | Cheapest bound |
| Keyset pagination | | Fixes deep offsets but changes the API |

**Trade-offs**
Clients depending on large pages are truncated.

**Validation**
Time and memory of `GET /items/?limit=N` at increasing N on seeded staging data (`not-safe-on-production`). Add a test that over-cap limits are rejected.

### PERF-003 — Argon2 hashing on the shared thread pool with no throttling

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `backend/app/crud.py:45` |
| **Tags** | needs-measurement |

**Problem**
Login, signup, user creation and password change run memory-hard Argon2 hashing (also for unknown emails via a dummy hash) in sync handlers on the shared thread pool, with no rate limiting.

**Performance principle**
CPU-heavy work on a shared bounded executor takes capacity from every other request; unauthenticated-reachable heavy work should be throttled.

**Evidence**
`crud.py:52` (dummy hash `m=65536,t=3,p=4` verified for missing users), `login.py:20` (unauthenticated sync login), `Dockerfile` (4 workers). No runtime evidence.

**Impact**
Critical path, per request, O(1) each but shared-resource contention under bursts, service-wide blast radius.

**Conditions**
Bursts of logins or signups. Hash time and thread-pool size are not in the repository, so no threshold is stated.

**Counter-evidence**
No rate limiting or dedicated executor found. 8-day tokens keep steady-state logins infrequent (bounds impact).

**Why this might not matter**
The hash cost is deliberate and login rates may be far below saturation.

**Recommendation**
Keep hash strength. Rate limit auth endpoints at the proxy, measure hash time and thread-pool occupancy, and add an isolated bounded executor only if measurement requires it.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Proxy rate limiting | **preferred** | Bounds work without weakening hashing |
| Dedicated executor | | Adds tuning; needs measurement |
| Lower Argon2 cost | | Weakens security |

**Trade-offs**
Rate limits can reject legitimate bursts.

**Validation**
Measure unrelated `GET /items/` latency while N concurrent logins run (`not-safe-on-production`). Falsifier: latency unchanged.

### PERF-004 — Synchronous SMTP while holding a DB connection and worker thread

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | io |
| **Location** | `backend/app/api/routes/login.py:54` |
| **Tags** | needs-measurement |

**Problem**
`POST /password-recovery/{email}` (unauthenticated), `create_user` and `test-email` send mail synchronously in the handler. In the recovery path the session holds a pooled connection from the user lookup until the request ends.

**Performance principle**
Slow external I/O must not be done while holding scarce shared resources on a user-blocking path.

**Evidence**
`login.py:67` (send inside handler after DB lookup), `utils.py:46` (no timeout in `smtp_options`), `db.py:5` (default pool settings). No background task or queue exists. No runtime evidence.

**Impact**
Critical path, per request, growth unknown, service-level blast radius if SMTP is slow.

**Conditions**
SMTP enabled and slow or failing, with concurrent requests for registered emails. Pool and thread-pool sizes in effect are unverified.

**Counter-evidence**
`emails` library default timeout not verified (lowers confidence). Mail is only sent for existing users (bounds impact).

**Why this might not matter**
SMTP is normally fast and the endpoint low-traffic; only failure modes are affected.

**Recommendation**
Release the session before sending, deliver via FastAPI background tasks (or a queue) with an explicit SMTP timeout, and set pool size and timeout deliberately.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Background task + timeout | **preferred** | Smallest change |
| External queue | | Durable, heavier |
| Timeout only | | Still holds the connection |

**Trade-offs**
Lost caller-visible send errors; lost mail on crash without a durable queue.

**Validation**
Delayed stub SMTP in staging; watch pool checkouts and latency (`not-safe-on-production`). Falsifier: connection released before send or SMTP times out quickly.
