## 1. Decision summary

### Overall assessment

A small ASP.NET Core / EF Core service (SQLite by default, SQL Server optional) with no committed measurements, so every finding is static and capped at High/Medium confidence. Nothing is critical. The most material issues are the absence of any secondary index on the columns every request looks up by (slug, username, email, created-at) and an eager-loading query shape that multiplies rows and fetches unused columns on the article list. Review confidence: Medium.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P2)** | Add indexes on Article.Slug, Person.Username, Person.Email, Article.CreatedAt and move to migrations | Affects every handler; cheap; but severity depends on table size (unknown) |
| 2 | **PERF-002 (P2)** | Project the article list to a DTO (no Body, counts via subqueries) | High confidence from code; per-request on the hottest read endpoint |
| 3 | **PERF-003 (P2)** | Cap Limit and bound comments/tags reads | Removes worst-case unbounded responses |

## 7. Findings

### PERF-001 — No secondary indexes on lookup and ordering columns
**Severity:** Medium | **Confidence:** Medium | **Priority:** P2 | **Category:** data-access | **Root cause:** ROOT-001
**Location:** `src/Conduit/Infrastructure/ConduitContext.cs:29` (`OnModelCreating`) | **Tags:** scalability-risk, needs-measurement

- **Problem:** The model has no `HasIndex`/`[Index]`; schema comes from `EnsureCreated` with no migrations. Lookups by Slug, Username, Email and the CreatedAt ordering have no supporting index beyond EF's PK/FK conventions.
- **Principle:** Selective lookups must use an access path whose cost does not grow with table size.
- **Evidence:** `ConduitContext.cs:29` (no index config; grep found none under `src`); `Program.cs:125` (EnsureCreated); Slug lookups in `Articles/Details.cs:30`, Edit, Favorites, Comments; Username lookups in nearly all authenticated handlers; Email in `Users/Login.cs`; `Articles/List.cs:105` orders by CreatedAt. No runtime evidence.
- **Impact:** Critical path, per request, O(n) in table size, service-wide.
- **Conditions:** Tables large enough that scan exceeds seek; sizes unknown (assumed to grow beyond demo size).
- **Counter-evidence:** No incidental index found (uniqueness is enforced only in code). Default is a small local SQLite file, which lowers confidence.
- **Why this might not matter:** For a demo-scale dataset (low thousands of rows) scans are negligible.
- **Recommendation:** Add unique indexes on Slug and Username, an index on Email, and a (CreatedAt, ArticleId) index; adopt migrations.
- **Alternatives:** Add indexes (preferred; fixes access path and enforces uniqueness); in-memory caching (rejected; adds invalidation and leaves the scan on miss).
- **Trade-offs:** Write cost and storage; unique indexes can fail on existing duplicates.
- **Validation:** `EXPLAIN QUERY PLAN` on representative data should change SCAN to SEARCH (safe-on-production, on a copy). Falsified if plans already use indexes or latency is unchanged.

### PERF-002 — Article queries multiply rows and fetch unused data
**Severity:** Medium | **Confidence:** High | **Priority:** P2 | **Category:** data-access | **Root cause:** ROOT-002
**Location:** `src/Conduit/Features/Articles/List.cs:31`, `ArticleExtensions.cs:11` | **Tags:** scalability-risk, needs-measurement

- **Problem:** `GetAllData` eager-loads two sibling collections (favorites, tags) in one query (no `AsSplitQuery`), so rows multiply per article. The list also fetches `Body` then nulls it (`List.cs:114`) and transfers every favorite row only to count it (`Article.cs:21`).
- **Principle:** Fetch only what the response needs; avoid cross-product joins of independent collections.
- **Evidence:** `ArticleExtensions.cs:11-13`; `List.cs:108,114`; `Domain/Article.cs:21`; reused in `Details.cs:30`, Favorites, Edit. No runtime evidence.
- **Impact:** Critical path, per request, grows with favorites x tags per article; endpoint-level.
- **Conditions:** Articles with many favorites/tags; page size up to caller-supplied Limit. Data distribution unknown.
- **Counter-evidence:** Skip/Take bounds the page; no repo configuration changes EF's single-query default.
- **Why this might not matter:** Typical articles have few favorites and tags; default page is 20.
- **Recommendation:** Project to a list DTO: no Body, favorites count and Favorited via subqueries, tags loaded separately.
- **Alternatives:** DTO projection (preferred); `AsSplitQuery` (removes cross product but still moves favorites and Body).
- **Trade-offs:** Serialization path changes (entity serialized today); split queries add round trips.
- **Validation:** Log SQL for `GET /api/articles?limit=20` on articles with many favorites; rows per page should equal page size (safe-on-production). Run `dotnet test tests/Conduit.IntegrationTests --filter FullyQualifiedName~Articles` (safe-on-production). Falsified if SQL is already split or data has no multi-favorite articles.

### PERF-003 — Unbounded read results (comments, tags, article limit)
**Severity:** Medium | **Confidence:** Medium | **Priority:** P2 | **Category:** data-access | **Root cause:** ROOT-003
**Location:** `src/Conduit/Features/Comments/List.cs:21` | **Tags:** scalability-risk, needs-measurement

- **Problem:** Comments list loads all comments and authors with tracking; tags list loads all tags; article list `Limit` has no maximum.
- **Principle:** Every response and query should be bounded independent of data growth.
- **Evidence:** `Comments/List.cs:23`; `Tags/List.cs:21`; `Articles/List.cs:109`. No runtime evidence.
- **Impact:** Critical path, per request, O(n), endpoint-level.
- **Conditions:** Articles with many comments, a growing free-form tag vocabulary, or clients sending very large limits; volumes unknown.
- **Counter-evidence:** The RealWorld spec does not require paging; no rate limiting found in `Program.cs`.
- **Why this might not matter:** Most articles have few comments and tag sets are small; paging changes the API contract.
- **Recommendation:** Cap Limit, use AsNoTracking and a documented maximum for comments/tags.
- **Alternatives:** Cap and AsNoTracking now (preferred); cache tags (rejected; does not bound the miss path, needs invalidation).
- **Trade-offs:** Behaviour change for clients using large limits; comment paging is a contract change.
- **Validation:** Measure row count and response size for the three endpoints on representative data (safe-on-production). Falsified if a gateway already caps and data is small.

### PERF-004 — Follow graph transferred in full for membership checks
**Severity:** Low | **Confidence:** High | **Priority:** P3 | **Category:** data-access | **Root cause:** ROOT-004
**Location:** `src/Conduit/Features/Profiles/ProfileReader.cs:35` | **Tags:** quick-win

- **Problem:** `ReadProfile` loads the user's whole Following and Followers just to run `Any`; the list endpoint loads all followed ids then `Contains` per author; the feed loads all Followers first.
- **Evidence:** `ProfileReader.cs:35`; `List.cs:123`; `List.cs:38`.
- **Impact:** Critical path, per authenticated request, O(follows); cost is transfer, not CPU.
- **Conditions:** Users following very many people; counts unknown.
- **Counter-evidence:** Contains runs over at most the page of authors.
- **Recommendation:** Keyed EXISTS query on (ObserverId, TargetId); filter by page author ids.
- **Trade-offs:** More or more complex queries; behaviour unchanged.
- **Validation:** Rows read from FollowedPeople per profile request should drop to at most one (safe-on-production).

### PERF-005 — Synchronous Count() in async handler
**Severity:** Low | **Confidence:** High | **Priority:** P3 | **Category:** concurrency | **Root cause:** ROOT-005
**Location:** `src/Conduit/Features/Articles/List.cs:133` | **Tags:** quick-win

- **Problem:** `queryable.Count()` blocks a request thread; it also re-applies the includes.
- **Evidence:** `List.cs:133` is the only synchronous DB call in the handler.
- **Impact:** Critical path, per request; matters under high concurrency or with SQL Server (SQLite is in-process).
- **Conditions:** High concurrency or slow database.
- **Counter-evidence:** SQLite default makes blocking brief.
- **Recommendation:** `await CountAsync(...)` on a filter-only query.
- **Trade-offs:** None significant.
- **Validation:** Thread pool queue length under concurrent list requests (safe-on-production). Falsified if no starvation is observed.

### Adjacent findings — outside performance scope

#### SEC-001 — Fast hard-coded-key password hash and hard-coded JWT key
**Kind:** security | **Confidence:** High | **Risk:** High (a single fast HMAC pass is cheap to brute-force and signing material is in source)

- **Problem:** `PasswordHasher` hashes password+salt once with HMAC-SHA512 under a constant key; the JWT signing key is a literal in `AddJwt`.
- **Evidence:** `Infrastructure/Security/PasswordHasher.cs:11`; `ServicesExtensions.cs:51`.
- **Recommendation:** Use PBKDF2/Argon2/bcrypt with a suitable cost and load signing keys from secret configuration.
- **Trade-offs:** Slower login by design; requires hash migration on next login.
- **Validation:** Not a performance question; assess with a dedicated application security review.
