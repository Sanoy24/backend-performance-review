## 1. Decision summary

### Overall assessment

A small ASP.NET Core 10 / EF Core / Mediator REST API (SQLite by default, SQL Server optional) with no instrumentation, benchmarks or load tests. Static analysis finds two scalability risks that matter if the data grows: the schema has no indexes on the columns every request looks up (Slug, Username, Email), and the article list endpoint has no page-size cap while over-fetching favorite and tag rows. Everything else is minor or bounded. Review confidence is Medium: source is fully read, but no workload or runtime data exists, so all workload-dependent findings are capped at Medium confidence.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-002 (P1)** | Add unique indexes on Article.Slug, Person.Username, Person.Email (plus migrations) | Every request does at least one such lookup; cheap and also enforces uniqueness |
| 2 | **PERF-001 (P1)** | Clamp `limit` and replace collection Includes in the list query with COUNT/EXISTS projections | Hottest read endpoint; cost scales with favorites x tags and with client-chosen limit |
| 3 | **PERF-004 (P2)** | Stop loading whole follow collections for membership checks | Affects every authenticated list and profile request |

## 7. Findings

### PERF-001 — GET /articles and /articles/feed accept a client-supplied limit with no upper bound, and every row is material

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/List.cs:26` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
GET /articles and /articles/feed accept a client-supplied limit with no upper bound, and every row is materialised with two collection Includes (all favorite rows and all tag rows per article) just to compute a favorites count and a tag list.

**Performance principle**
Work per request must be bounded by a server-enforced limit, and a query should fetch only the data the response needs (a count, not every row that is counted).

**Evidence**
- Limit is passed straight from the query string to Take(message.Limit ?? 20); no cap or validator exists for this query. (`src/Conduit/Features/Articles/List.cs:109`)
- GetAllData() Includes Author, ArticleFavorites and ArticleTags: two sibling collections in one query, producing a favorites x tags row product per article in the single-query default. (`src/Conduit/Features/Articles/ArticleExtensions.cs:11`)
- Favorited and FavoritesCount are computed from the loaded ArticleFavorites list, so every favorite row is transferred only to be counted. (`src/Conduit/Domain/Article.cs:26`)
- Offset pagination via Skip(message.Offset ?? 0) over an ordered join; deep pages scan and discard skipped rows. (`src/Conduit/Features/Articles/List.cs:108`)
- No runtime evidence exists in the repository (no benchmark, load test, trace or query log was found).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters when articles accumulate many favorites and tags, or a client requests a large limit. Assumed (not stated anywhere in the repo): a public home feed hitting this endpoint on every page view with non-trivial favorite counts. Rows read per page = sum over returned articles of max(1,favorites) x max(1,tags) (derivation from the Include shape); with default limit 20 this stays small until favorites per article reach the hundreds.

**Counter-evidence**
- Default page size is 20 when limit is absent, which bounds the common case. (bounds-impact)
- Searched for a response cache, output cache, max-limit clamp or AsSplitQuery; none found. (no-effect)

**Why this might not matter**
This is a RealWorld demo app backed by SQLite by default (Program.cs); with small datasets and the default limit of 20, the row product is tiny and the endpoint is probably fast enough.

**Recommendation**
Clamp limit server-side (for example to a documented maximum) and project the list response instead of Including collections: compute FavoritesCount with a correlated COUNT, the current user's Favorited with an EXISTS, and tags via a projected string list or AsSplitQuery. Optionally move to keyset pagination on (CreatedAt, ArticleId), which the ORDER BY already matches.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Project to a DTO with COUNT/EXISTS subqueries and a limit clamp | **preferred** | Removes the transferred rows entirely rather than reshaping how they are fetched. |
| Keep Includes but add AsSplitQuery |  | Removes the cartesian product but still transfers every favorite row. |
| Cache the list response |  | Masks the work and needs invalidation on every favorite/edit; hit rate is unknown. |

**Trade-offs**
A projection changes the shape of the serialised entity (Article is currently serialised directly), so the response contract needs a DTO and tests; a limit clamp is a visible API behaviour change for clients passing large limits.

**Validation**
Metric: SQL rows returned and command duration for GET /api/articles?limit=20 and limit=1000 against a dataset with many favorites per article. Expectation: Rows per request scale with limit only (not with favorites x tags); request with large limit is clamped. Falsifier: If the captured SQL shows rows per article equal to 1 even with many favorites, or p95 latency is unchanged with the projection on a realistic dataset, the finding is not material. Safety: not-safe-on-production.

### PERF-002 — The schema is created with EnsureCreated and the model declares no index on Article

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:19` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
The schema is created with EnsureCreated and the model declares no index on Article.Slug, Person.Username or Person.Email, yet nearly every request resolves its target by one of these columns.

**Performance principle**
Lookups by a high-frequency predicate must be served by an index so cost grows with matches, not with table size.

**Evidence**
- No HasIndex or [Index] anywhere in the source; OnModelCreating configures only composite keys and conversions. (`src/Conduit/Infrastructure/ConduitContext.cs:19`)
- Schema is produced by EnsureCreated, and the repo has no migrations, so the model is the only source of indexes (EF adds indexes for foreign keys by convention, not for these columns). (`src/Conduit/Program.cs:124`)
- Slug lookup on article details, edit, delete, comments and favorites. (`src/Conduit/Features/Articles/Details.cs:30`)
- Username lookup on virtually every authenticated handler, for example persons by Username == current user. (`src/Conduit/Features/Articles/Create.cs:52`)
- Login resolves the person by Email. (`src/Conduit/Features/Users/Login.cs:45`)
- No runtime evidence exists in the repository (no benchmark, load test, trace or query log was found).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Pays off once the Articles or Persons tables are large enough that a scan is measurable. Assumed: tables grow beyond thousands of rows in a real deployment; the repo gives no row counts. Handlers issue several such lookups per request (for instance Favorites.Add does an article slug lookup, a username lookup and a re-read).

**Counter-evidence**
- EF Core creates indexes on foreign key columns by convention, so Comments.ArticleId, ArticleTags.TagId, ArticleFavorites.PersonId and FollowedPeople.TargetId are likely indexed; this finding is limited to the non-key lookup columns. (bounds-impact)
- Searched for migrations, SQL scripts or raw DDL adding indexes; none found. (no-effect)
- Slug uniqueness is also not enforced by a constraint, so an index that doubles as a unique index is the natural fix. (no-effect)

**Why this might not matter**
With SQLite and a few hundred rows in a demo database a scan costs microseconds; the finding only bites with real data volume, which no file states.

**Recommendation**
Declare a unique index on Article.Slug, a unique index on Person.Username and on Person.Email in OnModelCreating (and introduce migrations if production data already exists, since EnsureCreated will not add them to an existing database). Consider an index on Article.CreatedAt (with ArticleId) to serve the list ordering.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Unique indexes via model configuration plus migration | **preferred** | Fixes the scan and also enforces the uniqueness the slug loop currently only checks in application code. |
| Cache person and article lookups in memory |  | Adds invalidation complexity and does not help first lookups. |

**Trade-offs**
Slightly slower writes and more storage; unique indexes can fail on existing duplicate data (slug and email) and need a data cleanup before applying.

**Validation**
Metric: Query plan for SELECT ... WHERE Slug = @p and WHERE Username = @p (SCAN vs SEARCH ... USING INDEX). Expectation: Plan changes from full-table scan to index search. Falsifier: If the plan already shows an index search (for example an index created outside the model) or table sizes are tiny and latency is unchanged, drop the finding. Safety: safe-on-production.

### PERF-003 — GET /articles/{slug}/comments loads the entire article together with all of its comments and each comment's au

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Comments/List.cs:23` |
| **Tags** | scalability-risk |

**Problem**
GET /articles/{slug}/comments loads the entire article together with all of its comments and each comment's author through tracked Includes, with no paging or limit, and the whole article row (including Body) is transferred just to reach the comments.

**Performance principle**
Response size and work must be bounded, and queries should read only what the response needs.

**Evidence**
- Articles.Include(Comments).ThenInclude(Author).FirstOrDefaultAsync loads every comment; no Take, no AsNoTracking. (`src/Conduit/Features/Comments/List.cs:23`)
- Comments are kept on the Article via a List<Comment> navigation, so the join returns the article columns once per comment row. (`src/Conduit/Domain/Article.cs:19`)
- No runtime evidence exists in the repository (no benchmark, load test, trace or query log was found).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters for articles with large comment threads (assumption: popular articles reach hundreds or more comments; nothing in the repo states this). Article body is repeated on each joined row, so transfer is roughly comments x body size (derivation from the join shape).

**Counter-evidence**
- Most articles are expected to have few comments, which bounds the typical case. (bounds-impact)
- The upstream API spec returns all comments unpaginated; paging would change the contract. (bounds-impact)

**Why this might not matter**
The endpoint's contract returns the full list, and typical comment counts are small; the cost is likely negligible outside a few hot articles.

**Recommendation**
Query Comments directly (Comments.AsNoTracking().Where(c => c.Article.Slug == slug).Include(Author)) so the article body is not re-read, and add an optional limit/offset or a server cap for very large threads if the contract allows.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Query Comments table directly with AsNoTracking | **preferred** | Removes the repeated article columns and change tracking with no contract change. |
| Add pagination |  | Bounds growth but changes the API contract; do it only if hot threads are measured. |

**Trade-offs**
Directly querying comments loses the article-not-found check unless a separate existence query is kept (one extra cheap query).

**Validation**
Metric: Bytes and rows returned by the SQL for GET comments on an article with many comments. Expectation: Rows unchanged, bytes per row drop by the article body size. Falsifier: If comment counts per article are small (single digits) in production data, ignore. Safety: not-safe-on-production.

### PERF-004 — Membership questions about the current user's follows are answered by loading whole follow collections: ReadPr

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Profiles/ProfileReader.cs:35` |
| **Tags** | scalability-risk |

**Problem**
Membership questions about the current user's follows are answered by loading whole follow collections: ReadProfile Includes both Following and Followers (Following is never used), the feed path Includes all Followers, and every authenticated article list loads all followed ids into memory.

**Performance principle**
Answer an existence or membership question with a bounded, indexed predicate rather than materialising the whole relation.

**Evidence**
- ReadProfile includes Following and Followers on the current person, then runs Followers.Any(...) in memory; Following is not read. (`src/Conduit/Features/Profiles/ProfileReader.cs:37`)
- Feed path loads currentUser with Include(Followers) and then filters with an IN list of target ids. (`src/Conduit/Features/Articles/List.cs:38`)
- Every authenticated list request loads all of the user's followed ids and calls List.Contains per article author. (`src/Conduit/Features/Articles/List.cs:123`)
- No runtime evidence exists in the repository (no benchmark, load test, trace or query log was found).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters when logged-in users follow many people (assumption: follow counts reach hundreds or thousands for some users; unknown). ReadProfile is also called from Followers Add/Delete and the profile endpoint.

**Counter-evidence**
- Typical follow counts are probably small, bounding the common case. (bounds-impact)
- FollowedPeople has a composite key (ObserverId, TargetId), so a direct existence query would be index-backed. (no-effect)

**Why this might not matter**
For users following tens of people the extra rows are trivial; the cost is only noticeable for outliers.

**Recommendation**
Replace the collections with FollowedPeople.AnyAsync(f => f.Observer.Username == u && f.TargetId == id) in ReadProfile, drop the unused Following Include, and in List restrict the followed-ids query to the authors on the page (Where(TargetId in pageAuthorIds)) and use an EXISTS subquery for the feed filter.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Targeted existence/IN queries limited to page authors | **preferred** | Cost bounded by page size, not follow count. |
| Cache follow sets per user |  | Needs invalidation on follow/unfollow; unproven benefit. |

**Trade-offs**
Slightly more query code; no consistency change.

**Validation**
Metric: Rows read from FollowedPeople per GET /profiles/{u} and authenticated GET /articles for a user with many follows. Expectation: Rows read independent of follow count. Falsifier: If follow counts per user are small in production, the change gives no measurable gain. Safety: not-safe-on-production.

### PERF-006 — Article creation looks up each tag individually, saves each new tag with its own SaveChangesAsync, and finds a

| | |
|:--|:--|
| **Root cause** | `ROOT-006` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/Create.cs:57` |
| **Tags** | quick-win |

**Problem**
Article creation looks up each tag individually, saves each new tag with its own SaveChangesAsync, and finds a unique slug with one query per candidate suffix (the same slug loop exists in Edit).

**Performance principle**
Round trips per request should be constant or batched, not proportional to the number of items in the payload.

**Evidence**
- foreach over TagList issues FindAsync and, for new tags, SaveChangesAsync inside the loop. (`src/Conduit/Features/Articles/Create.cs:59`)
- Slug uniqueness loops AnyAsync once per candidate suffix; each probe hits the unindexed Slug column (see PERF-002). (`src/Conduit/Features/Articles/Create.cs:74`)
- Same slug loop in Edit. (`src/Conduit/Features/Articles/Edit.cs:95`)
- No runtime evidence exists in the repository (no benchmark, load test, trace or query log was found).

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: endpoint.

**Conditions**
Round trips = tags in the request (FindAsync, plus a save per new tag) plus 1 + k slug probes where k is the number of existing articles with the same slug. Write endpoints are lower-traffic than reads; both counts are small for typical posts.

**Counter-evidence**
- Tag count per article is normally a handful and duplicate titles are uncommon, which bounds the cost. (bounds-impact)

**Why this might not matter**
Article creation is a rare write; a few extra round trips are unlikely to matter.

**Recommendation**
Fetch all requested tags in one query (Where(t => names.Contains(t.TagId))), add the missing ones and save once, and resolve slug collisions with a single StartsWith query for the base slug.

**Trade-offs**
Slightly more code; a single batched save widens the window for concurrent duplicate-tag inserts, so a unique key conflict must be handled.

**Validation**
Metric: SQL commands per POST /articles with 5 new tags. Expectation: Command count drops from proportional-to-tags to constant. Falsifier: If SQL logging shows the commands are already batched, the finding is wrong. Safety: not-safe-on-production.

### PERF-007 — The total article count is computed with synchronous queryable

| | |
|:--|:--|
| **Root cause** | `ROOT-007` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Features/Articles/List.cs:133` |
| **Tags** | quick-win |

**Problem**
The total article count is computed with synchronous queryable.Count() inside an otherwise async handler, blocking a thread-pool thread for the duration of the count query.

**Performance principle**
Do not block threads on I/O in an async request path; threads are a shared, finite resource.

**Evidence**
- ArticlesCount = queryable.Count() (sync) in an async ValueTask Handle that awaits all other calls. (`src/Conduit/Features/Articles/List.cs:133`)
- No runtime evidence exists in the repository (no benchmark, load test, trace or query log was found).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters with a networked database (SQL Server provider is supported in Program.cs) under concurrent load where blocked threads delay thread-pool injection. With the default SQLite provider the call is effectively synchronous anyway.

**Counter-evidence**
- Default provider is SQLite, whose I/O is synchronous in practice, so the thread-blocking cost is minimal there. (bounds-impact)

**Why this might not matter**
Only meaningful on SQL Server under high concurrency; one line change but low payoff otherwise.

**Recommendation**
Use await queryable.CountAsync(cancellationToken).

**Trade-offs**
None material.

**Validation**
Metric: Thread-pool queue length / blocked threads during a concurrent load test on GET /articles. Expectation: No synchronous DB calls on the request path. Falsifier: If thread pool counters are flat with and without the change, it is immaterial. Safety: not-safe-on-production.

- HMACSHA512 keyed with a literal string, one pass over password+salt. (`src/Conduit/Infrastructure/Security/PasswordHasher.cs:11`)
- Hash comparison uses SequenceEqual. (`src/Conduit/Features/Users/Login.cs:61`)
- JWT signing key literal in source. (`src/Conduit/ServicesExtensions.cs:49`)

**Impact** A leaked database allows fast offline guessing because one HMAC pass is cheap, and the source-embedded keys are shared by every deployment; Medium because exploitation needs a prior data leak or source access.

**Recommendation** Use a purpose-built password hashing function (PBKDF2/Argon2 via Identity's PasswordHasher), CryptographicOperations.FixedTimeEquals for comparison, and load signing keys from secret configuration.

**Trade-offs** Existing hashes must be migrated on next login; a slower hash adds deliberate CPU cost per login.

**Validation** Run the dedicated review below.

**Would need** A dedicated application security review (threat model, credential storage and key management audit).
