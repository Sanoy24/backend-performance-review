## 1. Decision summary

### Overall assessment

A small ASP.NET Core / EF Core service whose main weaknesses are in the data-access layer: no secondary indexes on the columns every request filters by, an uncapped list limit, and a wide multi-collection Include for article reads. No runtime evidence exists, so all findings are static-analysis conclusions at Medium review confidence; the most important thing to know is that nothing in the schema supports the lookups the handlers perform, which will show as table scans once data grows.

### Top three actions

| Order | Finding | Action | Why now |
|:--|:--|:--|:--|
| 1 | **PERF-001 (P1)** | Add unique indexes on Person.Username/Email and Article.Slug and an index for CreatedAt ordering | Every request does these lookups; cheap fix |
| 2 | **PERF-003 (P1)** | Clamp `limit` in a validator on the list query | A single request can ask for the whole table |
| 3 | **PERF-002 (P2)** | Replace GetAllData Includes with a narrow projection (or split query); do not load Body in lists | Row multiplication favorites x tags on the hottest read |

| Production row counts | Severity of PERF-001/002/005 | Row counts from the deployed DB |
| Provider (SQLite vs SQL Server) and gateway limits | PERF-003/004/007 impact | Deployment config |

## 7. Findings

### PERF-001 — No secondary indexes on the columns every request filters by (Slug, Username, Email, CreatedAt)

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | High |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:147` |
| **Stable ID** | `a1a6f02d99164197` |
| **Tags** | quick-win, scalability-risk |

**Problem**
The model declares no index on Article.Slug, Person.Username, Person.Email or Article.CreatedAt, yet nearly every handler filters or sorts on them, so each lookup is a table scan as data grows.

**Performance principle**
Lookups by a non-key attribute must be satisfied by an access path whose cost is sublinear in table size.

**Evidence** (static only; no runtime evidence exists)

- OnModelCreating configures only composite keys and foreign keys for ArticleTag, ArticleFavorite, FollowedPeople; no HasIndex anywhere (a repo-wide search for Index/HasIndex in src found nothing). (`src/Conduit/Infrastructure/ConduitContext.cs`:147)
- Schema is created via EnsureCreated from the model, with no migrations, so the model is the only place an index could be declared. (`src/Conduit/Program.cs`)
- Article lookups by Slug: Details, Comments List/Create, Favorites, Edit, Delete (e.g. Details.cs FirstOrDefaultAsync x.Slug == ...). (`src/Conduit/Features/Articles/Details.cs`:28)
- Person lookups by Username on every authenticated write/read (Create article, Comments Create, Favorites Add, Followers, ProfileReader, feed) and by Email on login. (`src/Conduit/Features/Users/Login.cs`:45)
- Article list orders by CreatedAt desc, ArticleId desc with Skip/Take. (`src/Conduit/Features/Articles/List.cs`:105)

**Impact**
Position: critical path for almost all endpoints. Frequency: per request, several lookups each. Growth: linear in Articles/Persons row count. Blast radius: service-wide, since scans share the single database.

**Conditions**
Matters once the Articles or Persons tables grow beyond what fits comfortably in cache pages; no row counts are supplied, so the threshold is unknown (assumed: production-sized data, not demo data). SQLite and SQL Server both scan without an index (uniqueness of these columns is only by application convention).

**Counter-evidence**
- Searched for HasIndex/[Index]/migrations/raw SQL DDL; found none. Primary keys and FK indexes (ArticleTag, ArticleFavorite composite keys; FK columns) exist implicitly, which covers join paths but not the lookups above. (effect: bounds-impact)

**Why this might not matter**
At demo or small scale the tables fit in memory and scans are cheap; the app also does not enforce unique usernames/slugs by index, so adding unique indexes has a data-migration cost.

**Recommendation**
Declare indexes in OnModelCreating: unique on Person.Username, unique on Person.Email, unique on Article.Slug, and an index on Article.CreatedAt (descending, with ArticleId) for the list ordering. Unique indexes also remove the application-level race on slug/username uniqueness checks.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Declare indexes in the model (preferred): removes scans at the source | **preferred** | addresses the access path directly |
| Cache user/article lookups |  | masks the scan and adds invalidation cost |

**Trade-offs**
Slower writes and more storage per index; unique indexes can fail on pre-existing duplicate data and require a cleanup step; EnsureCreated will not alter an existing database, so a migration is needed.

**Validation**
Metric: Query plan for WHERE Slug=@p and WHERE Username=@p, plus p95 latency of GET /api/articles/{slug}. Expectation: Plan changes from table scan to index seek; latency becomes flat with table size. Falsifier: Plans already show index seeks (e.g. indexes added out of band) or latency does not vary with row count. Safety: safe-on-production.
- `sqlite3 realworld.db "EXPLAIN QUERY PLAN SELECT * FROM Articles WHERE Slug = 'x';"  -- run against a copy of the database` — Show whether the slug lookup scans (SQLite) (safe-on-production)

### PERF-002 — Article reads join two child collections in one query and over-fetch article bodies

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/ArticleExtensions.cs:9` |
| **Stable ID** | `77e2ecc5980dd7cb` |
| **Tags** | scalability-risk |

**Problem**
GetAllData Includes Author, ArticleFavorites and ArticleTags in a single non-split query, so each article row is repeated favorites x tags times; the list handler also loads full bodies only to null them afterwards.

**Performance principle**
Do not multiply result rows by joining independent one-to-many relations in one query; fetch only the columns the response uses.

**Evidence** (static only; no runtime evidence exists)

- Two sibling collection Includes in one query with no AsSplitQuery configured (UseSqlite/UseSqlServer called without query splitting options). (`src/Conduit/Features/Articles/ArticleExtensions.cs`:9)
- List loads full Article rows (including Body), then sets article.Body = null before returning. (`src/Conduit/Features/Articles/List.cs`:113)
- Favorite entities are loaded in full only to compute FavoritesCount/Favorited from the collection count. (`src/Conduit/Domain/Article.cs`:32)
- Used by List, Details, Favorites Add/Delete. (`src/Conduit/Features/Favorites/Add.cs`:70)

**Impact**
Position: critical path (public list/detail). Frequency: per returned article. Growth: rows per article = favorites x tags (derivation from the two Includes), so it grows multiplicatively with popular articles. Blast radius: endpoints that use GetAllData.

**Conditions**
Matters when articles accumulate many favorites and several tags each; for a page of 20 articles the cost is the sum of per-article favorites x tags. Favorite counts are unknown.

**Counter-evidence**
- Looked for AsSplitQuery/QuerySplittingBehavior in Program.cs and the context; none found. (effect: no-effect)
- Tags per article are typically few, which bounds the multiplier on one side. (effect: bounds-impact)

**Why this might not matter**
Typical articles have a handful of tags and tens of favorites; with default page size 20 the extra rows may be negligible compared to network and serialization.

**Recommendation**
Project only the fields the response needs (including FavoritesCount via a subquery COUNT and tag names), or use AsSplitQuery; skip Body in the list projection rather than load and null it.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Select into a DTO projection (preferred): removes both row multiplication and body transfer | **preferred** | does the minimum work |
| AsSplitQuery: fixes multiplication but still loads favorites rows and bodies |  |  |

**Trade-offs**
Projection duplicates mapping logic away from the domain type serialized today; split queries add round trips (a transaction is present, so consistency is kept).

**Validation**
Metric: Row count returned by the list SQL for a page, and p95 of GET /api/articles. Expectation: Rows per page drop from sum(favorites x tags) toward the page size. Falsifier: Logged SQL already shows one row per article. Safety: safe-on-production.

### PERF-003 — Article list accepts an uncapped caller-supplied limit and offset

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | High |
| **Confidence** | High |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/List.cs:108` |
| **Stable ID** | `9659a60400c1ff90` |
| **Tags** | scalability-risk, quick-win |

**Problem**
Limit and Offset come straight from the query string and are passed to Take/Skip with no upper bound, so one request can ask for the whole table.

**Performance principle**
Every result set returned to a caller must have a server-enforced upper bound.

**Evidence** (static only; no runtime evidence exists)

- Take(message.Limit ?? 20) and Skip(message.Offset ?? 0) with no clamp or validator on Query. (`src/Conduit/Features/Articles/List.cs`:108)
- No validator is defined for the List Query; the controller passes the parameters through. (`src/Conduit/Features/Articles/ArticlesController.cs`)
- A large Offset also forces the database to read and discard Offset rows (offset pagination).

**Impact**
Position: critical path, public list endpoint. Frequency: per request. Growth: linear in the limit chosen by the caller, multiplied by the PERF-002 row duplication. Blast radius: service-wide (memory, DB, serialization).

**Conditions**
Reachable by any client; matters whenever the Articles table is larger than a page, including accidental clients that set a huge limit.

**Counter-evidence**
- Searched for Math.Min/clamps, a max-page-size option and a validator on List.Query; none found. (effect: no-effect)

**Why this might not matter**
If an API gateway enforces query-string limits, the cap may exist upstream; none is visible in the repository.

**Recommendation**
Clamp Limit to a documented maximum (and reject negatives) in a Query validator; consider keyset pagination on (CreatedAt, ArticleId) if deep offsets are expected.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Clamp limit in a validator (preferred) | **preferred** | minimal and removes the unbounded case |
| Keyset pagination |  | also fixes deep-offset cost but changes the API contract |

**Trade-offs**
Clients relying on very large limits break; keyset pagination changes the RealWorld spec shape.

**Validation**
Metric: Response size and DB rows read for GET /api/articles?limit=100000 against a seeded database. Expectation: Result is clamped to the maximum. Falsifier: Endpoint already returns at most the cap. Safety: not-safe-on-production.
- `curl -s "http://localhost:5000/api/articles?limit=100000" | wc -c  -- run against a local seeded instance` — Measure response size for an oversized limit (not-safe-on-production)

### PERF-004 — Synchronous COUNT executed on a request thread in an otherwise async handler

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Features/Articles/List.cs:133` |
| **Stable ID** | `d696bbab16140b67` |
| **Tags** | quick-win |

**Problem**
ArticlesCount is computed with the synchronous queryable.Count(), blocking a thread-pool thread during the database call, and runs a second query over the same filtered set.

**Performance principle**
Do not block threads on I/O in a request path that is otherwise non-blocking.

**Evidence** (static only; no runtime evidence exists)

- queryable.Count() inside an async method, while the page itself uses ToListAsync. (`src/Conduit/Features/Articles/List.cs`:133)

**Impact**
Position: critical path. Frequency: per list request. Growth: one blocked thread per request for the duration of the COUNT; COUNT cost itself grows with matching rows. Blast radius: endpoint, but can contribute to thread-pool starvation under concurrency.

**Conditions**
Matters under high concurrent list traffic with a slow COUNT (large Articles tables, no index on filter columns); negligible at low concurrency.

**Counter-evidence**
- The SQLite provider is effectively synchronous underneath, so the async benefit differs by provider; SQL Server is the case where it matters. (effect: lowers-confidence)

**Recommendation**
Use await queryable.CountAsync(cancellationToken) and issue the count without the Includes.

**Trade-offs**
None material.

**Validation**
Metric: Thread-pool queue length / thread count during a list load test. Expectation: No blocked threads attributable to the handler. Falsifier: No change in thread-pool metrics under load. Safety: safe-on-production.

### PERF-005 — Comments and tags endpoints return unbounded collections

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Comments/List.cs:22` |
| **Stable ID** | `4c1b132f42c71ace` |
| **Tags** | scalability-risk |

**Problem**
Comments List loads the whole article and every comment with its author in one query and returns all of them; Tags List returns every tag. Neither paginates, and Comments Create also loads all existing comments just to add one.

**Performance principle**
Every result set returned to a caller must have a server-enforced upper bound.

**Evidence** (static only; no runtime evidence exists)

- Articles.Include(Comments).ThenInclude(Author) loads the full article (including Body) plus all comments, tracked, and returns article.Comments. (`src/Conduit/Features/Comments/List.cs`:22)
- Tags.OrderBy(TagId).ToListAsync() with no limit. (`src/Conduit/Features/Tags/List.cs`:20)
- Comments Create Includes all existing comments to add one. (`src/Conduit/Features/Comments/Create.cs`:37)

**Impact**
Position: critical path. Frequency: per request. Growth: linear in comments per article and in total tags. Blast radius: endpoint.

**Conditions**
Matters for articles with large comment threads (hot articles) and as the tag vocabulary grows; sizes unknown (assumed: production-sized data).

**Counter-evidence**
- The upstream RealWorld spec does not paginate comments or tags, which explains the design and limits what can change without breaking clients. (effect: bounds-impact)

**Why this might not matter**
Comment threads and tag lists are often small, and the spec does not require pagination.

**Recommendation**
Query comments directly (Comments.Where(ArticleId).AsNoTracking() with projection) instead of loading the article; in Create, check article existence without loading comments; add a server-side cap or optional paging for comments and tags.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Query comments directly and skip loading all comments in Create (preferred, spec-compatible) | **preferred** | removes avoidable work without an API change |
| Add pagination parameters |  | changes the contract |

**Trade-offs**
A cap changes behavior for very large threads; direct queries need a separate existence check.

**Validation**
Metric: Rows read and bytes returned for GET comments on an article with many comments; query count for POST comment. Expectation: POST comment no longer reads existing comments. Falsifier: SQL log already shows no comments read on POST. Safety: safe-on-production.

### PERF-006 — Verbose-level synchronous console logging is hard-wired for every environment

| | |
|:--|:--|
| **Root cause** | `ROOT-005` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | observability |
| **Location** | `src/Conduit/ServicesExtensions.cs:110` |
| **Stable ID** | `0185725b3f912050` |
| **Tags** | quick-win, needs-measurement |

**Problem**
Serilog is configured at MinimumLevel.Verbose with a themed console sink and no configuration override, so every request and EF command is written to the console.

**Performance principle**
Per-request instrumentation must have bounded, configurable cost and must not sit on the request path at maximum verbosity.

**Evidence** (static only; no runtime evidence exists)

- MinimumLevel.Verbose() with only a Console sink; the code comment says 'just for local debug' but the method is called unconditionally. (`src/Conduit/ServicesExtensions.cs`:114)
- AddSerilogLogging is invoked in Program.cs startup with no environment check and no use of appsettings. (`src/Conduit/Program.cs`)
- The Dockerfile/docker-compose deploy path runs the same binary. (`Dockerfile`)

**Impact**
Position: every request. Frequency: per request, several log events (framework and EF command logs). Growth: O(1) per request but scales with traffic. Blast radius: service-wide, via the console sink's synchronous writes.

**Conditions**
Matters when the app runs outside local debugging at meaningful request rates (assumed); console throughput and container log capture cost are unmeasured.

**Counter-evidence**
- The comment indicates local-debug intent; no environment gate was found anyway. (effect: lowers-confidence)

**Why this might not matter**
For a demo app at low traffic the logging cost is small and the verbosity is arguably desirable.

**Recommendation**
Read the minimum level from configuration (Information or Warning by default), override EF and Microsoft.AspNetCore namespaces to Warning, and use an async sink for production.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Configuration-driven levels (preferred) | **preferred** | keeps debug available locally |
| Remove Serilog |  | loses useful logs |

**Trade-offs**
Less detail in production logs.

**Validation**
Metric: Log events per request and p95 latency with level Verbose vs Warning under the same load. Expectation: Lower latency and CPU at Warning. Falsifier: No measurable difference. Safety: not-safe-on-production.

### PERF-007 — Every request, including read-only queries, opens a database transaction

| | |
|:--|:--|
| **Root cause** | `ROOT-006` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs:27` |
| **Stable ID** | `e010583e71208e04` |
| **Tags** | none |

**Problem**
The mediator pipeline calls BeginTransaction for every message and commits afterwards, using synchronous Begin/Commit calls, so reads pay extra round trips and hold a connection for the whole handler.

**Performance principle**
Do not pay coordination cost (transactions, connection holding) for operations that need no atomicity.

**Evidence** (static only; no runtime evidence exists)

- Behavior registered globally for all requests. (`src/Conduit/ServicesExtensions.cs`:26)
- Database.BeginTransaction (sync) and Commit (sync) in ConduitContext. (`src/Conduit/Infrastructure/ConduitContext.cs`:229)

**Impact**
Position: every handler. Frequency: per request. Growth: O(1). Blast radius: service-wide but a small constant.

**Conditions**
Noticeable on SQL Server with network latency where BEGIN/COMMIT are extra round trips; on local SQLite it is cheap. Pool size is default and unknown.

**Counter-evidence**
- In-memory provider skips the transaction; SQLite default is local so cost is small. (effect: bounds-impact)

**Recommendation**
Apply the transaction behavior only to command handlers (marker interface), and use async BeginTransactionAsync/CommitAsync.

**Trade-offs**
Read handlers lose a shared snapshot unless a snapshot isolation level is chosen.

**Validation**
Metric: DB round trips per GET request. Expectation: Two fewer round trips per read on SQL Server. Falsifier: Provider logs show no BEGIN/COMMIT on reads. Safety: safe-on-production.

### PERF-008 — Article creation issues per-tag lookups and per-tag saves plus a slug probe loop

| | |
|:--|:--|
| **Root cause** | `ROOT-007` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/Create.cs:58` |
| **Stable ID** | `5d15ed9e92441c68` |
| **Tags** | none |

**Problem**
Create does a FindAsync per tag and a SaveChangesAsync for each new tag, then probes AnyAsync for slugs in a loop, so a single create costs O(tags + slug collisions) round trips.

**Performance principle**
Batch writes and lookups; avoid per-item round trips for variable-size input.

**Evidence** (static only; no runtime evidence exists)

- foreach tag: FindAsync, then AddAsync + SaveChangesAsync when missing. (`src/Conduit/Features/Articles/Create.cs`:58)
- for loop with AnyAsync per candidate slug, unindexed (see PERF-001). (`src/Conduit/Features/Articles/Create.cs`:74)

**Impact**
Position: critical path of article creation. Frequency: per tag and per slug collision. Growth: linear in tags supplied (not capped by the validator) and in duplicate titles. Blast radius: endpoint.

**Conditions**
Matters for creates with many tags or many same-titled articles; write rate unknown and likely much lower than reads.

**Counter-evidence**
- Tag count is client-controlled but typically small; no cap found in the validator. (effect: bounds-impact)

**Recommendation**
Load existing tags with one Where(Contains) query, add all missing tags and the article in a single SaveChanges, and rely on a unique Slug index plus retry instead of a probe loop.

**Trade-offs**
Concurrent creates of the same new tag need conflict handling.

**Validation**
Metric: Statements per POST /api/articles with N tags. Expectation: Constant instead of growing with N. Falsifier: SQL log shows a constant statement count already. Safety: safe-on-production.

### SEC-001 — Hard-coded JWT signing key and weak password hashing

| | |
|:--|:--|
| **Kind** | Security |
| **Confidence** | High |
| **Risk** | High |
| **Location** | `src/Conduit/ServicesExtensions.cs:48` |

**Problem** The JWT signing key is a hard-coded literal, and passwords are hashed with a single HMAC-SHA512 pass using a constant key rather than a password KDF.

**Evidence** ServicesExtensions.cs:48 (key literal); PasswordHasher.cs:16 (constant HMAC key, single pass).

**Impact** Anyone with source access can forge tokens, and leaked hashes are cheap to brute-force; hence High risk.

**Recommendation** Load the signing key from secret configuration; use PBKDF2/Argon2/bcrypt with per-user salt.

**Trade-offs** Existing hashes and tokens are invalidated; a migration path is required.

**Validation** Run the dedicated review below.

**Would need** A dedicated security review of authentication and secret handling.
