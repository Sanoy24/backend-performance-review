## 1. Decision summary

### Overall assessment

A small ASP.NET Core / EF Core service (SQLite by default) with no instrumentation and no runtime evidence. The material issues are data-access shape problems that grow with data: the article read model loads and joins whole relations (PERF-001), and no lookup column is indexed (PERF-002). The rest are bounded or constant-factor costs. Review confidence is Medium: the whole source tree was read, but no workload or data volume exists, so workload-dependent findings are capped at Medium confidence.

## 7. Findings

### PERF-001 - Article reads join two sibling collections and load every favorite row to count them

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/ArticleExtensions.cs:9` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
GetAllData() Includes Author, ArticleFavorites and ArticleTags in a single (non-split) query, so each returned article produces favorites x tags joined rows, and every favorite row is materialized only so Article.FavoritesCount/Favorited can read List.Count.

**Performance principle**
Work and transferred data should scale with what the response needs (a count and a short tag list), not with the product of two independent one-to-many relations.

**Evidence**
- GetAllData includes Author, ArticleFavorites, ArticleTags with no AsSplitQuery. (`src/Conduit/Features/Articles/ArticleExtensions.cs:9`)
- FavoritesCount is ArticleFavorites.Count and Favorited is Count != 0, so the whole favorites collection is loaded to produce an integer and a boolean. (`src/Conduit/Domain/Article.cs`)
- GetAllData is used by article list, detail, favorite add/delete and edit re-reads. (`src/Conduit/Features/Articles/List.cs:31`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-item; growth: O(n^2)+; blast radius: endpoint.

**Conditions**
Matters when popular articles accumulate many favorites and carry several tags; rows returned per article = favorites x tags (derivation from the two Includes). With few favorites per article it is negligible. Actual data distribution is unknown (assumption), hence Medium confidence.

**Counter-evidence**
- Take(limit) is applied to the article set, so row multiplication is per returned article and bounded by page size times favorites x tags. (effect: bounds-impact)
- No data-volume or distribution evidence exists in the repo; tag count per article is user-supplied and favorites are unbounded per article. (effect: lowers-confidence)

**Why this might not matter**
For a demo-scale deployment with tens of articles and few favorites, the multiplication is trivial and cost is dominated by process overhead.

**Recommendation**
Compute favorites count and tag list by projection (Select to a response shape with a Count subquery and tag ids), or at minimum use AsSplitQuery for the two collections; do not load favorite rows when only a count is needed.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Project to a response shape with a count subquery | **preferred** | Removes the loaded rows entirely rather than reshaping how they are fetched. |
| AsSplitQuery on GetAllData |  | Removes the cartesian product but still loads every favorite row and adds a round trip. |
| Denormalized FavoritesCount column |  | Adds write-path consistency cost; only justified if measurement shows counting is hot. |

**Trade-offs**
Projection changes response-building code and the Article entity's computed properties; split queries add round trips and a consistency window outside a transaction.

**Validation**
Metric: Rows returned and query time for GET /api/articles?limit=20 over seeded articles with many favorites and tags. Expectation: Row count drops from favorites x tags per article to one row per article (direction certain; magnitude data-dependent). Falsifier: If rows per article are already near one on realistic data, the finding does not matter. Safety: not-safe-on-production.

### PERF-002 - No indexes on Slug/Username/Email/CreatedAt lookup and sort columns

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:25` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
The model declares no index; schema comes from EnsureCreated, which indexes only keys and foreign keys. Slug, Username, Email lookups and the CreatedAt ordering will scan the table.

**Performance principle**
Selective lookups on a growing table need an access path whose cost does not grow linearly with table size.

**Evidence**
- Search for Index/Unique/HasIndex across src finds no declarations; OnModelCreating only configures keys, relationships and date conversions. (`src/Conduit/Infrastructure/ConduitContext.cs:25`)
- Schema is created by EnsureCreated, not migrations. (`src/Conduit/Program.cs:103`)
- Articles are looked up by Slug in Details, Edit, Delete, Favorites, Comments; AnyAsync(Slug) loops run on create and edit. (`src/Conduit/Features/Articles/Details.cs:30`)
- Persons are looked up by Username on authenticated mutations and the list, and by Email on login and register. (`src/Conduit/Features/Articles/List.cs:73`)
- Article list orders by CreatedAt desc, ArticleId desc with Skip/Take. (`src/Conduit/Features/Articles/List.cs:106`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters once articles/persons reach a size where a scan is noticeable (assumption: thousands of rows or more; actual volume unknown). Negligible at demo scale. A deployed database could carry manually-added indexes, which the repo does not evidence.

**Counter-evidence**
- Searched for HasIndex, [Index], Unique, migrations: none found. (effect: no-effect)
- A deployed database could have manually-added indexes; nothing in the repo shows it. (effect: lowers-confidence)

**Why this might not matter**
If the deployment stays small (a demo/reference app on the default SQLite file), scans over a few thousand rows are cheap.

**Recommendation**
Add unique indexes on Person.Username, Person.Email and Article.Slug (uniqueness is also assumed by the code's own duplicate checks) and an index on Article.CreatedAt. Introduce migrations since EnsureCreated will not alter an existing database.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Indexes via HasIndex plus migrations | **preferred** | Addresses the access path and enforces uniqueness the code assumes. |
| Cache user lookups per request |  | Masks scans without fixing them and adds invalidation. |

**Trade-offs**
Slightly slower writes and more storage; migrations must be introduced with a backfill for existing databases; unique constraints fail if duplicates exist.

**Validation**
Metric: Query plans for Slug, Username and CreatedAt queries on a representative copy. Expectation: Plans change from SCAN to SEARCH on the new indexes. Falsifier: If plans already show index seeks (indexes exist in the real database), the finding is void. Safety: not-safe-on-production.

### PERF-003 - Article list: unbounded limit, deep offset, synchronous Count, Body loaded then discarded

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/List.cs:105` |
| **Tags** | quick-win |

**Problem**
limit defaults to 20 but has no upper bound; offset paging scans and discards rows; the total uses the synchronous queryable.Count() in an async handler, a second blocking database call; Body is read for every listed article and then nulled.

**Performance principle**
Work per request must be bounded by the server, not by caller-supplied parameters; do not block threads on I/O; do not read data to discard it.

**Evidence**
- Take(message.Limit ?? 20) with no clamp; Limit comes straight from the query string. (`src/Conduit/Features/Articles/List.cs:109`)
- ArticlesCount = queryable.Count() is synchronous. (`src/Conduit/Features/Articles/List.cs:133`)
- Controller binds int? limit/offset without validation. (`src/Conduit/Features/Articles/ArticlesController.cs:19`)
- Body is loaded by the entity query and then set to null in a loop. (`src/Conduit/Features/Articles/List.cs:116`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters when the table is large or a client passes a very large limit; discarded Body cost grows with article size. On the default SQLite provider the async API is largely synchronous anyway, so the blocking Count matters mostly on SQL Server.

**Counter-evidence**
- Default limit 20 bounds ordinary clients. (effect: bounds-impact)
- Searched for a global max-page-size or validator for List.Query: none found. (effect: no-effect)

**Why this might not matter**
Only abusive or misconfigured clients pass a huge limit, and the default is small; thread-pool impact of one sync Count is modest.

**Recommendation**
Clamp limit and reject negative offsets, await CountAsync, and project away Body instead of loading and nulling it; consider keyset paging if deep offsets are expected.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Clamp limit, CountAsync, project away Body | **preferred** | Directly bounds and trims the work. |
| Keyset pagination |  | Changes the limit/offset contract the RealWorld spec defines. |

**Trade-offs**
Clamping changes behavior for clients asking for more than the cap; check against the API spec tests.

**Validation**
Metric: Rows and bytes read for GET /api/articles?limit=100000 and database calls per request. Expectation: Rows capped at the maximum; Count becomes async. Falsifier: If limit is already capped upstream by a gateway, impact is nil. Safety: not-safe-on-production.

### PERF-004 - Comment endpoints load the whole comment collection, including on create

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | memory |
| **Location** | `src/Conduit/Features/Comments/List.cs:23` |
| **Tags** | scalability-risk |

**Problem**
Comment listing returns all comments with authors, tracked and unpaginated; Comments.Create does Include(x => x.Comments) just to append one comment, so each write costs O(existing comments).

**Performance principle**
Writes should not read the whole collection they append to; reads of unbounded collections need a bound or lean projection.

**Evidence**
- Include(Comments).ThenInclude(Author) with tracking, FirstOrDefaultAsync by slug. (`src/Conduit/Features/Comments/List.cs:23`)
- Create loads all comments with Include(x => x.Comments) then article.Comments.Add(comment). (`src/Conduit/Features/Comments/Create.cs:36`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters for articles with hundreds or thousands of comments (assumed; no data). Typical articles have few.

**Counter-evidence**
- The RealWorld spec returns all comments, so the read path is partly unbounded by contract. (effect: bounds-impact)
- Create's Include is removable without behavior change: the comment can be linked by foreign key. (effect: no-effect)

**Why this might not matter**
Low comment counts in the typical case; the read path is mandated by the API contract.

**Recommendation**
In Create, load the article without Include and attach the comment by foreign key; in List use AsNoTracking and project to the response shape.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Remove Include on create; AsNoTracking and projection on list | **preferred** | Eliminates the write-path O(n) with no contract change. |
| Paginate comments |  | Breaks the spec response. |

**Trade-offs**
Slightly more explicit code; nothing material.

**Validation**
Metric: Rows loaded per POST /articles/{slug}/comments on an article with many comments. Expectation: Rows loaded drop from N comments to 0 on create. Falsifier: If articles never exceed a handful of comments, no measurable change. Safety: not-safe-on-production.

**Performance principle**

Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters under sustained request load when container stdout is slow or captured; whether EF command events reach the sink depends on host filter configuration not visible in the repo.

**Counter-evidence**
- No logging filter configuration found that would suppress Information events; this does not prove none exists in production environment variables. (effect: lowers-confidence)

**Why this might not matter**
Console logging is cheap at low traffic and the comment says it is for local debugging.

**Recommendation**

**Validation**

### PERF-007 - Blanket per-request synchronous transaction, including reads

| | |
|:--|:--|
| **Root cause** | `ROOT-007` |
| **Severity** | Low |
| **Confidence** | Medium |
| **Priority** | P3 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs:17` |
| **Tags** | needs-measurement |

**Problem**
The pipeline behavior calls BeginTransaction/CommitTransaction (synchronous) around every handler, so even GETs hold a connection and a ReadCommitted transaction for the whole handler.

**Performance principle**
Hold scarce connections only as long as needed, and avoid synchronous I/O on async paths.

**Evidence**
- Behavior registered for all requests. (`src/Conduit/ServicesExtensions.cs:26`)
- Database.BeginTransaction and Commit are synchronous calls. (`src/Conduit/Infrastructure/ConduitContext.cs:83`)
- The hard-coded default is SQLite, where a write transaction serialises with other writers. (`src/Conduit/Program.cs:15`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-request; growth: O(1); blast radius: service.

**Conditions**
Matters mainly with SQL Server under high concurrency, where each request pins a connection for its duration; the effect is a constant per request. Pool size and load are unknown.

**Counter-evidence**
- Handlers make no external calls while holding the transaction, which keeps duration short. (effect: bounds-impact)

**Recommendation**
Open transactions only in command (write) handlers and use BeginTransactionAsync/CommitAsync.

**Trade-offs**
Commands that relied on a read transaction for consistency need review.

**Validation**
Metric: Connection hold time and pool wait for GET endpoints under load. Expectation: Pool wait decreases for read-heavy mixes. Falsifier: No change in pool wait means the transaction was not material. Safety: not-safe-on-production.

### PERF-008 - Per-item round trips in article create/edit (tags, slug probing)

| | |
|:--|:--|
| **Root cause** | `ROOT-008` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/Create.cs:59` |
| **Tags** | quick-win |

**Problem**
Create does FindAsync plus SaveChanges for each new tag in a loop, and Create and Edit probe slug uniqueness with an AnyAsync loop that repeats per collision.

**Performance principle**
Batch work over a variable-length input instead of one round trip per item.

**Evidence**
- foreach over TagList with FindAsync and an immediate SaveChangesAsync. (`src/Conduit/Features/Articles/Create.cs:59`)
- for loop with AnyAsync(Slug == uniqueSlug) incrementing a suffix. (`src/Conduit/Features/Articles/Create.cs:75`)
- Same slug loop in Edit. (`src/Conduit/Features/Articles/Edit.cs`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: endpoint.

**Conditions**
n is the number of tags in one request (user-supplied, unbounded) or the number of articles sharing a title; writes are rarer than reads.

**Counter-evidence**
- Typical articles have a few tags and unique titles. (effect: bounds-impact)

**Recommendation**
Load existing tags with one Where(Contains) query, add missing ones and save once; cap tag count in validation. Slug probing can query the slug prefix once and compute the next suffix.

**Trade-offs**
Concurrent creation of the same tag requires handling a unique violation.

**Validation**
Metric: Database commands per POST /articles with 10 new tags. Expectation: Commands drop from about two per tag to a constant (derivation from loop structure). Falsifier: If requests carry at most one tag, immaterial. Safety: not-safe-on-production.

**Problem**
GET /tags loads and sorts all tags each time and materializes full entities before projecting to strings.

**Performance principle**
Repeated identical reads of slowly changing data should not redo full work each time.

**Evidence**
- Tags.OrderBy(TagId).ToListAsync then Select TagId. (`src/Conduit/Features/Tags/List.cs:18`)
- Tags are inserted by any article create with user-controlled strings, so the set grows with usage. (`src/Conduit/Features/Articles/Create.cs:61`)
- No runtime evidence (no profile, EXPLAIN, trace, or load test) exists in the repository; this finding rests on source reading.

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters if distinct tag count becomes large (unknown) and the front end calls /tags on each page load (assumed; frontend not in repo).

**Counter-evidence**
- TagId is the primary key and rows are tiny. (effect: bounds-impact)

**Recommendation**
Project with Select(x => x.TagId); measure before considering any cache, and only then a short-lived cache with a stated staleness bound.

**Trade-offs**
Any cache adds staleness; projection has none.

**Validation**
Metric: Latency and row width of GET /api/tags with a large seeded tag table. Expectation: Row width shrinks; time scales with tag count. Falsifier: If tag count stays in the hundreds, no gain. Safety: not-safe-on-production.
