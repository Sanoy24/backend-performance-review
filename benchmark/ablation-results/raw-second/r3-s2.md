## 7. Findings

### PERF-001 - No indexes on the columns every handler filters by (Slug, Username, Email)

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:188` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
The model declares no index on Articles.Slug, Persons.Username or Persons.Email, yet nearly every handler resolves its target by one of those columns, so each lookup is a table scan as the tables grow.

**Performance principle**
Lookups by a selective key should cost proportional to the result, not to the table; an access path must exist for every high-frequency predicate.

**Evidence** (static only; no runtime evidence exists)
- OnModelCreating configures only composite keys, FKs and date conversions; no HasIndex/IsUnique anywhere in src (search for HasIndex/Index returned nothing). (`src/Conduit/Infrastructure/ConduitContext.cs`:188)
- Schema is created with EnsureCreated and there are no migrations, so the model above is the whole schema. (`src/Conduit/Program.cs`)
- Slug predicate: Articles.GetAllData().FirstOrDefault(x => x.Slug == ...) in Details; also Edit, Delete, Comments List/Create, Favorites Add. (`src/Conduit/Features/Articles/Details.cs`:34)
- Username predicate on authenticated requests: Persons.FirstAsync(x => x.Username == current user) in Articles Create, Comments Create, Favorites Add, Followers Add, ProfileReader. (`src/Conduit/Features/Articles/Create.cs`:31)
- Email predicate: Login and user Create/Edit uniqueness checks. (`src/Conduit/Features/Users/Login.cs`:33)

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters once Articles/Persons hold enough rows that a scan is measurable; row counts are not stated anywhere in the repo, so the crossover is unknown. Assumes neither provider has an automatic index on these columns (EF Core adds indexes only for foreign keys).

**Counter-evidence**
- Looked for HasIndex, unique constraints, migrations or raw SQL index creation; none exist. (no-effect)
- EF Core auto-creates indexes on foreign-key columns (AuthorId, ArticleId, TagId, PersonId), so joins are covered; only the three natural-key columns are exposed. (bounds-impact)
- No row-count data in the repo, so scan cost at realistic sizes is unmeasured. (lowers-confidence)

**Why this might not matter**
For a demo-sized dataset (this is the RealWorld reference implementation) a scan over a few thousand rows is negligible, and SQLite scans are fast.

**Recommendation**
Add HasIndex(x => x.Slug).IsUnique() on Article, and unique indexes on Person.Username and Person.Email in OnModelCreating, and ship them via a migration (EnsureCreated will not alter an existing schema). This also makes the existing check-then-insert uniqueness checks enforceable.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Unique indexes on Slug, Username, Email | **preferred** | Removes the scan and doubles as the integrity constraint. |
| Cache user/article lookups in memory |  | Adds invalidation problems and leaves the scan on a cache miss. |

**Trade-offs**
Index maintenance cost on writes (small); unique indexes make previously tolerated duplicate rows fail at migration time and turn races into constraint exceptions that need handling; EnsureCreated needs a migration path for existing databases.

**Validation**
Metric: Query plan for WHERE Slug = @p / Username = @p / Email = @p. Expectation: SCAN becomes SEARCH using the new index; direction only, magnitude unmeasured. Falsifier: Plan already uses an index (e.g. one created out of band in the deployed database) or latency is unchanged after adding it. Safety: safe-on-production. Guard: Integration test asserting the EF model declares the indexes.

### PERF-002 - Article reads join two sibling collections in one query and hydrate every favorite row

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/ArticleExtensions.cs:11` |
| **Tags** | scalability-risk, needs-measurement |

**Problem**
GetAllData includes Author, ArticleFavorites and ArticleTags in a single (non-split) query, so each article returns favorites x tags rows, and the full favorite rows are loaded only to compute a count and a boolean.

**Performance principle**
Rows transferred should track the information needed; joining independent one-to-many relations multiplies rows instead of adding them.

**Evidence** (static only; no runtime evidence exists)
- Two collection Includes with no AsSplitQuery. (`src/Conduit/Features/Articles/ArticleExtensions.cs`:11)
- Favorited/FavoritesCount are computed from the loaded ArticleFavorites list, so only a count is needed. (`src/Conduit/Domain/Article.cs`:29)
- GetAllData is used by article list, details, Edit (after save) and Favorites Add/Delete. (`src/Conduit/Features/Articles/List.cs`:31)

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: endpoint.

**Conditions**
Matters when popular articles accumulate many favorites and have several tags: rows per article = favorites x tags (derivation from the two collection joins). Default page size 20 bounds articles per request; actual favorite/tag counts are unknown.

**Counter-evidence**
- Looked for a global QuerySplittingBehavior in AddDbContext; none is set. (no-effect)
- Default page size is 20, which bounds articles per list request though not favorites per article. (bounds-impact)

**Why this might not matter**
Realistic articles carry a handful of tags and demo favorite counts are small; the cross product may stay in the tens of rows.

**Recommendation**
Project to a DTO with Select computing favorites count, favorited flag and tag names server-side (no favorite-row hydration), or at minimum add AsSplitQuery to GetAllData.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Select projection with Count() and tag-name list | **preferred** | Removes both the cross product and the favorite-row transfer. |
| AsSplitQuery |  | Removes the cross product but still transfers all favorite rows and adds round trips. |
| Denormalized favorites_count column |  | Consistency cost; not justified without measurements. |

**Trade-offs**
Response shape must keep matching the RealWorld contract (the NotMapped properties on Article would be replaced by a mapped DTO).

**Validation**
Metric: Rows returned and SQL command count for GET /api/articles with N favorites x M tags per article. Expectation: Rows per article drop from favorites x tags to 1; direction only. Falsifier: Logged SQL shows a split or grouped query and row counts do not multiply on a seeded dataset. Safety: safe-on-production. Guard: Integration test seeding an article with many tags and favorites and asserting query shape.

### PERF-003 - Synchronous Count() inside the async list handler blocks a request thread

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | High |
| **Priority** | P2 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Features/Articles/List.cs:133` |
| **Tags** | quick-win |

**Problem**
ArticlesCount = queryable.Count() runs a synchronous database call at the end of an otherwise async handler, blocking a thread-pool thread for the duration of the query on the main listing endpoint.

**Performance principle**
Blocking a shared worker thread on I/O reduces the number of concurrent requests the pool can serve; I/O waits should release the thread.

**Evidence** (static only; no runtime evidence exists)
- ArticlesCount = queryable.Count() while every other query uses ToListAsync/FirstOrDefaultAsync. (`src/Conduit/Features/Articles/List.cs`:133)
- The sync call is the final step of every list request, after up to four other awaited queries. (`src/Conduit/Features/Articles/List.cs`:105)

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters under concurrent load where list requests dominate and the count query is slow enough (large Articles table, unindexed filter columns) that threads wait; with a fast local SQLite file the block is short. Concurrency level unknown.

**Counter-evidence**
- ASP.NET Core has no synchronization context, so no deadlock, only thread blocking. (bounds-impact)
- Microsoft.Data.Sqlite async calls largely run synchronously anyway, so the gain on the default provider may be small; larger on SQL Server. (lowers-confidence)

**Why this might not matter**
With the default SQLite provider the async APIs complete synchronously, so the benefit may be nil there.

**Recommendation**
Replace with await queryable.CountAsync(cancellationToken), counting over a query without the Includes/ordering.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| CountAsync on a query without Includes | **preferred** | Removes thread blocking and lightens the SQL. |
| Leave as is for SQLite-only deployments |  | Valid only if SQL Server is never used. |

**Trade-offs**
None material.

**Validation**
Metric: Thread-pool queue length and throughput of GET /api/articles under concurrent load. Expectation: Fewer blocked threads under load against SQL Server; direction only. Falsifier: No change in thread-pool counters or throughput in a load test on the target provider. Safety: not-safe-on-production. Guard: Code review or analyzer rule forbidding synchronous EF calls in handlers.

### PERF-004 - Unbounded result sets: all tags, all comments per article, and uncapped list limit

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | memory |
| **Location** | `src/Conduit/Features/Tags/List.cs:26` |
| **Tags** | scalability-risk |

**Problem**
GET /tags loads and returns every tag row on each call, GET comments loads every comment (with authors, tracked) for an article, and the articles list accepts any client-supplied limit with no maximum.

**Performance principle**
Every response size should have an upper bound independent of data growth and client input.

**Evidence** (static only; no runtime evidence exists)
- Tags.OrderBy(...).ToListAsync with no Take. (`src/Conduit/Features/Tags/List.cs`:26)
- Articles.Include(Comments).ThenInclude(Author) without AsNoTracking or paging. (`src/Conduit/Features/Comments/List.cs`:24)
- Take(message.Limit ?? 20) with no upper clamp; Offset used as Skip, so cost grows with offset. (`src/Conduit/Features/Articles/List.cs`:108)
- Comment create also loads the article's full Comments collection just to add one. (`src/Conduit/Features/Comments/Create.cs`:35)

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters when the tag vocabulary or the comment count on a single popular article reaches thousands, or a client requests a very large limit; no data volumes are in the repo. The RealWorld spec does not mandate paging for tags/comments, hence Medium confidence.

**Counter-evidence**
- Looked for caps (Math.Min, validators, max page size) and response caching; none exist. (no-effect)
- Tags are usually a small controlled vocabulary, bounding the tags case. (bounds-impact)

**Why this might not matter**
Spec-conformant demo apps often have small tag and comment sets; paging would change the API contract for tags/comments.

**Recommendation**
Clamp limit to a maximum and validate offset >= 0, use AsNoTracking and a projection for comments (optionally a bounded page), avoid loading Comments in Comments Create (add by ArticleId), and consider caching tags only if measurement shows tag reads are hot.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Clamp limit + AsNoTracking + bounded comment page | **preferred** | Directly bounds response size. |
| Cache tags response |  | Does not bound the query on a miss; needs a staleness policy. |

**Trade-offs**
Clamping limit changes behavior for clients asking for more than the cap; comment paging changes the API contract.

**Validation**
Metric: Response bytes and rows for GET /api/tags, GET /api/articles/{slug}/comments and GET /api/articles?limit=100000 on seeded data. Expectation: Bounded response regardless of table size; direction only. Falsifier: Seeded dataset with many tags/comments shows flat latency and memory. Safety: safe-on-production. Guard: Test asserting the maximum limit is enforced.

### PERF-005 - Verbose-level synchronous console logging of every request and SQL command

| | |
|:--|:--|
| **Root cause** | `ROOT-005` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | observability |
| **Location** | `src/Conduit/ServicesExtensions.cs:110` |
| **Tags** | needs-measurement |

**Problem**
Serilog is configured at MinimumLevel.Verbose with a themed console sink, no async wrapper, no configuration override and no environment gate, so request and EF Core command logs (statement text included) are formatted and written to the console on the request thread.

**Performance principle**
Instrumentation on the hot path must have bounded overhead; synchronous I/O to a shared sink serializes requests.

**Evidence** (static only; no runtime evidence exists)
- MinimumLevel.Verbose() with WriteTo.Console(AnsiConsoleTheme.Code); the comment says 'just for local debug' but it is the only logging setup. (`src/Conduit/ServicesExtensions.cs`:113)
- Applied unconditionally after Build; there is no appsettings.json in the project. (`src/Conduit/Program.cs`:78)
- No metrics, tracing or health endpoints exist, so logs are the only telemetry. (`src/Conduit/Program.cs`)

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters at sustained request rates where the container's stdout is a pipe or log driver that applies backpressure; log lines per request scale with queries per request. Assumes framework default filtering at Information, which is not a file in the repo.

**Counter-evidence**
- Looked for appsettings.json log-level overrides or filters; none in the project. (no-effect)
- Default provider filters may drop Verbose/Debug framework categories, bounding volume to Information. (bounds-impact)

**Why this might not matter**
Console logging in a demo app is cheap relative to a local SQLite query, and the log lines are useful for debugging.

**Recommendation**
Drive level and sinks from configuration, default Microsoft.* and EF categories to Warning in production, and use an async/buffered sink if console output is kept. Add real metrics/tracing so performance work can be validated.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Config-driven levels + async sink | **preferred** | Keeps diagnostics while removing hot-path cost. |
| Remove logging |  | Loses diagnostics and the error middleware's output. |

**Trade-offs**
Less default diagnostic detail; an async sink can drop or reorder lines on crash.

**Validation**
Metric: Requests/sec and p95 latency of GET /api/articles with console logging at Verbose vs Warning under the same load. Expectation: Throughput rises or latency falls when logging is reduced; magnitude unmeasured. Falsifier: No measurable difference between logging levels. Safety: not-safe-on-production. Guard: Load-test CI job with a fixed log level.

### PERF-006 - Article create issues a query (and often a SaveChanges) per tag and probes slugs one query at a time

| | |
|:--|:--|
| **Root cause** | `ROOT-006` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/Create.cs:40` |
| **Tags** | quick-win |

**Problem**
For each requested tag the handler does a FindAsync and, if missing, a separate SaveChanges; slug uniqueness is checked by an AnyAsync loop that issues one query per collision.

**Performance principle**
Round trips should not scale with per-request input size when a set-based operation exists.

**Evidence** (static only; no runtime evidence exists)
- foreach tag: Tags.FindAsync then SaveChangesAsync inside the loop. (`src/Conduit/Features/Articles/Create.cs`:44)
- for (i...; AnyAsync(slug); i++) probing loop; same pattern in Edit. (`src/Conduit/Features/Articles/Create.cs`:62)

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: endpoint.

**Conditions**
Matters only for article writes with many new tags or many same-titled articles; writes are far rarer than reads in a typical blog and tagList length is client-controlled but unbounded in code.

**Counter-evidence**
- Looked for a tag-count limit in the validator; none. (no-effect)

**Recommendation**
Load existing tags with one Where(Contains) query, add all missing tags and the article in a single SaveChanges, and compute the slug suffix with a single StartsWith query (or rely on a unique index plus retry).

**Trade-offs**
Batching changes behavior on concurrent duplicate-tag inserts; needs unique-violation handling.

**Validation**
Metric: SQL command count for POST /api/articles with k new tags. Expectation: Constant instead of growing with k. Falsifier: Command count is already constant. Safety: safe-on-production. Guard: Integration test counting commands.

### PERF-007 - Every request, including pure reads, opens and commits an explicit database transaction synchronously

| | |
|:--|:--|
| **Root cause** | `ROOT-007` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs:21` |
| **Tags** | needs-measurement |

**Problem**
The mediator pipeline wraps all handlers in BeginTransaction/CommitTransaction using synchronous EF APIs, so read-only requests pay for extra BEGIN/COMMIT work, hold a connection for the whole handler, and block a thread at both ends.

**Performance principle**
Do not hold shared resources (connections, write locks) longer or with stronger guarantees than the work needs; avoid blocking calls in async paths.

**Evidence** (static only; no runtime evidence exists)
- context.BeginTransaction() / CommitTransaction() around every next(request). (`src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs`:26)
- BeginTransaction uses synchronous Database.BeginTransaction(IsolationLevel.ReadCommitted). (`src/Conduit/Infrastructure/ConduitContext.cs`:98)

**Impact**
Position: critical-path; frequency: per-request; growth: O(1); blast radius: service.

**Conditions**
Matters when the connection pool or SQLite file lock becomes contended (writes concurrent with many reads); effect per request is a small constant.

**Counter-evidence**
- Looked for a read-only opt-out of the behavior; none. SQLite deferred transactions bound the cost on the default provider. (bounds-impact)

**Recommendation**
Skip the transaction for query messages (marker interface or separate pipeline), and use BeginTransactionAsync/CommitAsync for commands.

**Trade-offs**
Reads lose the snapshot consistency of a single transaction across the handler's multiple queries.

**Validation**
Metric: DB commands per GET request (BEGIN/COMMIT present or not) and connection hold time. Expectation: Two fewer commands per read request; direction only. Falsifier: Provider logs show no BEGIN/COMMIT round trips for reads. Safety: safe-on-production. Guard: Test asserting query requests open no transaction.

### SEC-001 - Weak password hashing and hard-coded secrets

| | |
|:--|:--|
| **Kind** | security |
| **Confidence** | High |
| **Risk** | High |
| **Location** | `src/Conduit/Infrastructure/Security/PasswordHasher.cs:13` |

**Problem** Passwords are hashed with a single HMAC-SHA512 round under a hard-coded key, compared with non-constant-time SequenceEqual; the JWT signing key is also hard-coded in source.

**Evidence** HMACSHA512 with literal key; no iterations or work factor.; Hash comparison via SequenceEqual.; Hard-coded JWT signing key literal.

**Impact** Password hashes are cheap to brute-force if the database leaks and the signing key is public in source.

**Recommendation** Use a salted adaptive password hash (e.g. PBKDF2/Argon2 via ASP.NET Core Identity's hasher), compare with CryptographicOperations.FixedTimeEquals, and load signing keys from secret configuration.

**Trade-offs** Adaptive hashing adds login CPU cost.

**Validation** Run the review this needs.

**Would need** A dedicated security review; moving to an adaptive hash adds CPU cost to login that should then be load-tested.

## 9. Validation plan

### PERF-001

- **Baseline:** Query plan for WHERE Slug = @p / Username = @p / Email = @p - safe-on-production
- **Change:** Add HasIndex(x => x.Slug).IsUnique() on Article, and unique indexes on Person.Username and Person.Email in OnModelCreating, and ship them via a migration (EnsureCreated will not alter an existing schema). This also makes the existing check-then-insert uniqueness checks enforceable.
- **Expectation:** SCAN becomes SEARCH using the new index; direction only, magnitude unmeasured.
- **Falsifier:** Plan already uses an index (e.g. one created out of band in the deployed database) or latency is unchanged after adding it.
- **Guard:** Integration test asserting the EF model declares the indexes.
- **Commands:**
  - `safe-on-production` `sqlite3 realworld.db "EXPLAIN QUERY PLAN SELECT * FROM Articles WHERE Slug = 'x';"` - Show whether the Slug lookup scans (run against a copy or seeded DB).
- **Commands:**
  - `safe-on-production` `sqlite3 realworld.db ".indexes"` - List indexes actually present in the deployed schema.

### PERF-002

- **Baseline:** Rows returned and SQL command count for GET /api/articles with N favorites x M tags per article - safe-on-production
- **Change:** Project to a DTO with Select computing favorites count, favorited flag and tag names server-side (no favorite-row hydration), or at minimum add AsSplitQuery to GetAllData.
- **Expectation:** Rows per article drop from favorites x tags to 1; direction only.
- **Falsifier:** Logged SQL shows a split or grouped query and row counts do not multiply on a seeded dataset.
- **Guard:** Integration test seeding an article with many tags and favorites and asserting query shape.

### PERF-003

- **Baseline:** Thread-pool queue length and throughput of GET /api/articles under concurrent load - not-safe-on-production
- **Change:** Replace with await queryable.CountAsync(cancellationToken), counting over a query without the Includes/ordering.
- **Expectation:** Fewer blocked threads under load against SQL Server; direction only.
- **Falsifier:** No change in thread-pool counters or throughput in a load test on the target provider.
- **Guard:** Code review or analyzer rule forbidding synchronous EF calls in handlers.

### PERF-004

- **Baseline:** Response bytes and rows for GET /api/tags, GET /api/articles/{slug}/comments and GET /api/articles?limit=100000 on seeded data - safe-on-production
- **Change:** Clamp limit to a maximum and validate offset >= 0, use AsNoTracking and a projection for comments (optionally a bounded page), avoid loading Comments in Comments Create (add by ArticleId), and consider caching tags only if measurement shows tag reads are hot.
- **Expectation:** Bounded response regardless of table size; direction only.
- **Falsifier:** Seeded dataset with many tags/comments shows flat latency and memory.
- **Guard:** Test asserting the maximum limit is enforced.

### PERF-005

- **Baseline:** Requests/sec and p95 latency of GET /api/articles with console logging at Verbose vs Warning under the same load - not-safe-on-production
- **Change:** Drive level and sinks from configuration, default Microsoft.* and EF categories to Warning in production, and use an async/buffered sink if console output is kept. Add real metrics/tracing so performance work can be validated.
- **Expectation:** Throughput rises or latency falls when logging is reduced; magnitude unmeasured.
- **Falsifier:** No measurable difference between logging levels.
- **Guard:** Load-test CI job with a fixed log level.

### PERF-006

- **Baseline:** SQL command count for POST /api/articles with k new tags - safe-on-production
- **Change:** Load existing tags with one Where(Contains) query, add all missing tags and the article in a single SaveChanges, and compute the slug suffix with a single StartsWith query (or rely on a unique index plus retry).
- **Expectation:** Constant instead of growing with k.
- **Falsifier:** Command count is already constant.
- **Guard:** Integration test counting commands.

### PERF-007

- **Baseline:** DB commands per GET request (BEGIN/COMMIT present or not) and connection hold time - safe-on-production
- **Change:** Skip the transaction for query messages (marker interface or separate pipeline), and use BeginTransactionAsync/CommitAsync for commands.
- **Expectation:** Two fewer commands per read request; direction only.
- **Falsifier:** Provider logs show no BEGIN/COMMIT round trips for reads.
- **Guard:** Test asserting query requests open no transaction.

### Instrumentation gaps to close first

No metrics, tracing, or load-test harness exist. Add request latency and DB command metrics and a seeded load test before optimizing, so PERF-001 to PERF-005 can be baselined.
