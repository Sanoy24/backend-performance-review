## 7. Findings

### PERF-001 - No indexes on the columns every request filters by (Article.Slug, Person.Username, Person.Email, Article.CreatedAt)

| | |
|:--|:--|
| **Root cause** | `ROOT-001` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:87` |
| **Tags** | scalability-risk, quick-win |

**Problem**
The EF model declares no index on the lookup columns used by nearly every endpoint, so those lookups are table scans that grow with row count.

**Performance principle**
Selective lookups should cost proportional to the result size, not the table size; access paths must exist for the predicates and sort orders the hot paths use.

**Evidence**
- OnModelCreating configures only composite keys/FKs for ArticleTag, ArticleFavorite, FollowedPeople and DateTime conversions; no HasIndex anywhere. (`src/Conduit/Infrastructure/ConduitContext.cs:87`)
- grep for HasIndex/[Index] across src/Conduit returns nothing; Slug and Username/Email are plain string properties. (`src/Conduit/Domain/Article.cs:14`)
- Slug equality lookup is the entry of Details, Edit, Delete, Favorites, Comments list/create/delete (e.g. Details.cs:43-45, Comments/Create.cs:36-38). (`src/Conduit/Features/Articles/Details.cs:43`)
- Username equality lookup runs for the current user on feed, create, favorite, profile paths (e.g. Articles/Create.cs:42-45); Email lookup on every login and registration. (`src/Conduit/Features/Users/Login.cs:41`)
- Article list orders by CreatedAt DESC, ArticleId DESC with Skip/Take and no index on CreatedAt. (`src/Conduit/Features/Articles/List.cs:121`)
- Schema is created by EnsureCreated at startup; no migrations that could add indexes elsewhere. (`src/Conduit/Program.cs:120`)
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: service.

**Conditions**
Matters once Articles/Persons tables are large enough that a scan is not cheap; no table-size or traffic figure is supplied, so assumed: tables grow beyond tens of thousands of rows in production. Negligible for small demo datasets.

**Counter-evidence**
- Looked for HasIndex, [Index], unique constraints, and migrations; none found. (effect: no-effect)
- Table sizes are unknown and the shipped default is a local SQLite file, so scan cost may be negligible in practice; this caps confidence at Medium. (effect: lowers-confidence)

**Why this might not matter**
If the deployment is a demo/benchmark with a few hundred rows, scans on SQLite are microseconds and nothing here is observable.

**Recommendation**
Add indexes (unique where the domain demands: Person.Username, Person.Email, Article.Slug) and an index on Article(CreatedAt, ArticleId) via OnModelCreating, so lookups and the list ordering use an access path. Unique indexes also close the check-then-insert race (see COR-001).

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Add HasIndex/HasIndex().IsUnique() in the model | **preferred** | Removes the scan at the source and enforces uniqueness at no extra request cost. |
| Cache slug/username lookups in memory |  | Adds invalidation complexity and does not fix the list sort. |

**Trade-offs**
Extra write cost and storage per insert; EnsureCreated will not alter an existing database, so existing deployments need a manual migration/script. Unique indexes can fail to apply if duplicates already exist.

**Validation**
Metric: Query plan for SELECT by Slug / Username / Email and for the article-list ORDER BY; rows examined. Expectation: Plans change from table scan to index seek; rows examined per lookup drops from table size to about 1. Falsifier: Plans already show index use, or lookups on production-sized data are already sub-millisecond. Safety: safe-on-production.

### PERF-002 - Article list/detail load Author + Favorites + Tags as joined collections (row multiplication) and fetch the full Body that list responses discard

| | |
|:--|:--|
| **Root cause** | `ROOT-002` |
| **Severity** | High |
| **Confidence** | Medium |
| **Priority** | P1 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Articles/ArticleExtensions.cs:9` |
| **Tags** | scalability-risk |

**Problem**
GetAllData includes two collection navigations (ArticleFavorites, ArticleTags) in one query, so each article returns favorites x tags joined rows; the list handler also loads every article body only to set it to null.

**Performance principle**
Fetch only the data the response needs, and avoid joining independent one-to-many relations in one result set, which multiplies rows instead of adding them.

**Evidence**
- GetAllData includes Author, ArticleFavorites and ArticleTags with no AsSplitQuery. (`src/Conduit/Features/Articles/ArticleExtensions.cs:9`)
- List handler uses GetAllData, then sets article.Body = null for every row after materialisation. (`src/Conduit/Features/Articles/List.cs:31`)
- Favorites are fetched as full rows only so Favorited/FavoritesCount can use List.Count. (`src/Conduit/Domain/Article.cs:28`)
- Derivation: rows per article returned by the join = max(1,favorites) x max(1,tags); e.g. an article with 3 tags and 50 favorites yields 150 rows (illustrative inputs, not measured).
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters for the main list/feed endpoints when popular articles accumulate many favorites and several tags and the page size is the caller-supplied Limit (default 20). Assumed workload is read-heavy list traffic; unknown.

**Counter-evidence**
- Looked for AsSplitQuery/QuerySplittingBehavior configuration or projections; none found (UseSqlite(connectionString) without options). (effect: no-effect)
- Page is capped per request by Take(Limit ?? 20), but Limit has no upper bound in the handler. (effect: bounds-impact)

**Why this might not matter**
With small favorite/tag counts per article the product is tiny and EF's page subquery keeps it bounded; the Body column is usually modest in size.

**Recommendation**
Project to a response DTO in SQL (author fields, tag names, favorites count via correlated count, favorited flag via Any, no Body for list) instead of materialising entities with Includes; if entities are kept, use AsSplitQuery. Clamp Limit.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Select-projection with counts computed in the database | **preferred** | Removes both the row multiplication and unused columns. |
| AsSplitQuery |  | Removes the cartesian product but still transfers full favorite rows and Body. |
| Cache list pages |  | Hides cost, adds invalidation on favorite/edit. |

**Trade-offs**
DTO projection duplicates part of the Article JSON shape and changes serialization wiring; split query adds round trips.

**Validation**
Metric: Rows returned and bytes transferred by the GET /api/articles query; EF Core logged SQL. Expectation: Rows per page drop to the page size (<= Limit) and Body bytes disappear from list queries. Falsifier: Measured row count per page already equals page size on representative data. Safety: safe-on-production.

### PERF-003 - Whole follow lists are loaded into memory to answer a single membership check

| | |
|:--|:--|
| **Root cause** | `ROOT-003` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | data-access |
| **Location** | `src/Conduit/Features/Profiles/ProfileReader.cs:37` |
| **Tags** | scalability-risk |

**Problem**
ProfileReader loads the current user with both Following and Followers collections tracked, then calls Any on one of them; the feed path loads all Followers rows too and passes them to a Contains subquery.

**Performance principle**
Membership questions should be answered by the datastore with a keyed existence check, not by materialising a whole relationship.

**Evidence**
- Persons.Include(Following).Include(Followers) for the current user, then currentPerson.Followers.Any(TargetId == ...); Following is never read. (`src/Conduit/Features/Profiles/ProfileReader.cs:37`)
- Feed: Persons.Include(Followers) is materialised, then a Contains over its TargetIds is embedded in the article query. (`src/Conduit/Features/Articles/List.cs:37`)
- The same two Includes also create a followers x following row product in one query.
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters for users with large follow lists hitting profile and feed endpoints; follow-count distribution unknown, assumed to have a heavy tail.

**Counter-evidence**
- Looked for a follow-count limit; none exists in Followers/Add.cs. (effect: no-effect)
- Average users likely follow few people, bounding typical cost. (effect: lowers-confidence)

**Why this might not matter**
For typical accounts the loaded lists are small and the request is dominated by other work.

**Recommendation**
Replace with FollowedPeople.AnyAsync(f => f.Observer.Username == name && f.TargetId == id) and, for the feed, express the follow set as a subquery in SQL rather than loading it.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Keyed Any/subquery in SQL | **preferred** | Constant-size transfer. |
| Cache follow sets per user |  | Needs invalidation on follow/unfollow. |

**Trade-offs**
Slightly more verbose queries; none otherwise.

**Validation**
Metric: Rows read per GET /api/profiles/{u} and feed request. Expectation: Rows drop from follow-list size to 1. Falsifier: Follow lists in production are uniformly tiny. Safety: safe-on-production.

### PERF-004 - Comment endpoints load and track every comment of an article, unbounded; create/delete load them just to modify one

| | |
|:--|:--|
| **Root cause** | `ROOT-004` |
| **Severity** | Medium |
| **Confidence** | Medium |
| **Priority** | P2 |
| **Category** | memory |
| **Location** | `src/Conduit/Features/Comments/List.cs:22` |
| **Tags** | scalability-risk |

**Problem**
Comments list has no paging and is tracked, and Comments/Create and Delete load the article's full Comments collection to add or remove a single comment.

**Performance principle**
Per-request work and memory must be bounded by what the caller needs, not by the total size of a growing collection.

**Evidence**
- List: Articles.Include(Comments).ThenInclude(Author) with no limit or AsNoTracking. (`src/Conduit/Features/Comments/List.cs:22`)
- Create: Articles.Include(Comments) then article.Comments.Add(comment). (`src/Conduit/Features/Comments/Create.cs:36`)
- Delete: Articles.Include(Comments).ThenInclude(Author). (`src/Conduit/Features/Comments/Delete.cs:29`)
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters on articles with large comment threads (hot articles); the RealWorld API returns all comments, so listing cannot be fully bounded without a contract change. Thread sizes unknown.

**Counter-evidence**
- The API contract returns the full comment list, which bounds how much list can be reduced. (effect: bounds-impact)
- No comment cap or paging found. (effect: no-effect)

**Why this might not matter**
Typical article comment counts are small; only list is constrained by the API contract.

**Recommendation**
Make list AsNoTracking with a projection; in Create/Delete query the article id (AnyAsync/Select) and add or delete the comment by key without loading the collection.

**Alternatives**

| Option | | Why |
|:--|:--|:--|
| Key-based add/delete, no-tracking projected list | **preferred** | Removes load of unrelated comments on writes. |
| Paginate list |  | Breaks the expected response shape unless negotiated. |

**Trade-offs**
Slightly different EF patterns; list still returns all comments.

**Validation**
Metric: Rows loaded and allocations for POST /api/articles/{slug}/comments on an article with many comments. Expectation: Write cost becomes independent of existing comment count. Falsifier: Comment counts are always tiny. Safety: safe-on-production.

### PERF-005 - Article list issues a second, synchronous COUNT query on the request thread

| | |
|:--|:--|
| **Root cause** | `ROOT-005` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Features/Articles/List.cs:133` |
| **Tags** | quick-win |

**Problem**
queryable.Count() is the sync API called inside an async handler, blocking a thread-pool thread for the duration of a second round trip.

**Performance principle**
Do not block threads on I/O in an async path; blocked threads reduce capacity under concurrency.

**Evidence**
- ArticlesCount = queryable.Count() after the awaited page query. (`src/Conduit/Features/Articles/List.cs:133`)
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-request; growth: O(n); blast radius: endpoint.

**Conditions**
Matters only under high concurrency on a networked database (SQL Server); with local SQLite the I/O is in-process anyway. The count also scans because filters are unindexed (PERF-001).

**Counter-evidence**
- Default provider is in-process SQLite where blocking is cheap. (effect: bounds-impact)

**Recommendation**
Use await CountAsync(cancellationToken).

**Trade-offs**
None.

**Validation**
Metric: Thread-pool queue length / request latency under concurrent list load. Expectation: No blocked threads on the count call. Falsifier: Thread pool never saturates under target load. Safety: safe-on-production.

### PERF-006 - Every request, including pure reads, opens a synchronous ReadCommitted transaction

| | |
|:--|:--|
| **Root cause** | `ROOT-006` |
| **Severity** | Low |
| **Confidence** | Medium |
| **Priority** | P3 |
| **Category** | concurrency |
| **Location** | `src/Conduit/Infrastructure/ConduitContext.cs:160` |
| **Tags** | needs-measurement |

**Problem**
The mediator pipeline wraps every handler in BeginTransaction/Commit, using the synchronous Database.BeginTransaction.

**Performance principle**
Hold connections and locks only for work that needs them; avoid blocking calls on async paths.

**Evidence**
- DBContextTransactionPipelineBehavior calls context.BeginTransaction()/CommitTransaction() for all requests. (`src/Conduit/Infrastructure/DBContextTransactionPipelineBehavior.cs:27`)
- BeginTransaction uses sync Database.BeginTransaction(IsolationLevel.ReadCommitted). (`src/Conduit/Infrastructure/ConduitContext.cs:169`)
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-request; growth: O(1); blast radius: service.

**Conditions**
Matters mainly with SQLite writers (single-writer lock) or a small SQL Server pool under high concurrency; unmeasured and assumed small otherwise.

**Counter-evidence**
- Transaction ends with the handler, so hold time equals handler time; per-request O(1) overhead only. (effect: bounds-impact)

**Recommendation**
Skip the transaction for query handlers (e.g. via a marker interface) and keep it for commands.

**Trade-offs**
Reads lose transactional grouping across multiple statements in one handler.

**Validation**
Metric: Connection hold time and DB lock wait for read endpoints. Expectation: Read requests stop acquiring transactions. Falsifier: No measurable difference at target concurrency. Safety: safe-on-production.

### PERF-007 - Article create does per-tag FindAsync/SaveChanges and a slug-uniqueness probe loop with one query per collision

| | |
|:--|:--|
| **Root cause** | `ROOT-007` |
| **Severity** | Low |
| **Confidence** | High |
| **Priority** | P3 |
| **Category** | io |
| **Location** | `src/Conduit/Features/Articles/Create.cs:51` |
| **Tags** | - |

**Problem**
Each new tag is saved immediately in a loop (one round trip per tag, plus FindAsync each), and the slug loop issues one AnyAsync per suffix attempt.

**Performance principle**
Batch round trips instead of paying one per item.

**Evidence**
- foreach tag: FindAsync, then AddAsync + SaveChangesAsync inside the loop. (`src/Conduit/Features/Articles/Create.cs:51`)
- for-loop AnyAsync(Slug == uniqueSlug) increments the suffix until free; same pattern in Edit.cs. (`src/Conduit/Features/Articles/Create.cs:65`)
- No runtime evidence exists in the repository (no benchmarks, query plans, traces, or metrics).

**Impact**
Position: critical-path; frequency: per-item; growth: O(n); blast radius: endpoint.

**Conditions**
Matters for creates with many new tags or many same-titled articles (slug probes grow with number of collisions); expected to be small per request.

**Counter-evidence**
- Tag list per article is typically a handful; slug collisions require identical titles. (effect: bounds-impact)

**Recommendation**
Load all existing tags with one Contains query and add new Tag rows in one SaveChanges; fetch existing slugs with StartsWith(slug) once and pick the next suffix in memory.

**Trade-offs**
Race window on concurrent same-title/tag creates needs the unique indexes from PERF-001.

**Validation**
Metric: Statement count for POST /api/articles with N new tags. Expectation: Statement count independent of N. Falsifier: Tag lists are always 0-2. Safety: safe-on-production.

### SEC-001 - Passwords are hashed with a single HMAC-SHA512 pass keyed with the hard-coded string 'realworld' and a per-user salt; the JWT signing key is also a hard-coded literal

| | |
|:--|:--|
| **Kind** | Security |
| **Confidence** | High |
| **Risk** | High |
| **Location** | `src/Conduit/Infrastructure/Security/PasswordHasher.cs:52` |

**Problem** Passwords are hashed with a single HMAC-SHA512 pass keyed with the hard-coded string 'realworld' and a per-user salt; the JWT signing key is also a hard-coded literal. Hash comparison uses SequenceEqual (not constant time).

**Evidence**
- HMACSHA512 constructed from a literal key; single ComputeHashAsync, no iterations or memory-hard KDF. (`src/Conduit/Infrastructure/Security/PasswordHasher.cs:52`)
- Signing key is a literal in source. (`src/Conduit/ServicesExtensions.cs:252`)
- Login compares hashes with SequenceEqual. (`src/Conduit/Features/Users/Login.cs:57`)

**Impact** Risk High: credential theft from a leaked database or source is far easier than with a standard KDF, and tokens can be forged if the source key is used in production.

**Recommendation** Use a standard password hashing API (PBKDF2/Argon2/bcrypt via ASP.NET Identity's hasher), load the JWT key from secret configuration, and compare in constant time. The cheap hash is also why login is not a CPU hotspot; a proper KDF will make login CPU-heavy by design and should be capacity-tested.

**Trade-offs** Existing hashes must be migrated (rehash on next login); a proper KDF costs CPU per login.

**Validation** Run the review this needs.
